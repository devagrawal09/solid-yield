# DECISIONS — `@solidjs/blocks` build-out

Decision log for the blocks-library build-out on `blocks-lib`. One entry per decision: what was decided, the alternatives on the table, and why. New decisions append; a reversed decision is not edited but superseded by a new entry that names it. Forks of a topic branch are logged here too (see "Branch log").

> **Provenance.** The original of this file (26 entries, committed on `blocks-lib` in a container on 2026-10-04) was lost unpushed when that container's disk filled. This version was **reconstructed on 2026-10-04 from the session handoff**, which carried the decisions and their one-line rationale but not the full alternatives text. Where an entry's reasoning is thinner than it was, it says so. Entries whose content the handoff did not carry (D-015's text, D-025, D-026) are marked **lost** and left blank rather than invented. Per-entry ownership was not carried either: by D-002, design decisions are Dev's; process decisions were proposed by Claude and accepted by Dev. Re-affirm or correct any entry by appending, not editing.

Reading order with the rest of the plan: `yield-library.md` (the reference), this file, `yield-gate-baseline.md` (what "green" means).

> **Names (Phase 3).** Entries written in the Solid fork use the in-repo names `@solidjs/blocks`, `@solidjs/vite-plugin-blocks` and `@solidjs/eslint-plugin-blocks`, and the lint prefix `@solidjs/blocks/<rule>`. They are left as written (a log is not edited). Since the extraction's rename commit (D-011) the packages are `solid-blocks`, `vite-plugin-solid-blocks` and `eslint-plugin-solid-blocks`, and the lint prefix is `solid-blocks/<rule>`. Fork paths in entries (`documentation/plans/…`, `examples/blocks-harness`, `examples/<original>`) are `documentation/…`, `examples/harness` and `examples/originals/<original>` here.

> **Names (D-096).** Names before D-096: `solid-blocks` / block → `solid-yield` / routine; entries keep their original wording. In full: `solid-blocks`, `vite-plugin-solid-blocks`, `eslint-plugin-solid-blocks` and the lint prefix `solid-blocks/<rule>` are `solid-yield`, `vite-plugin-solid-yield`, `eslint-plugin-solid-yield` and `solid-yield/<rule>`; `packages/blocks`, `packages/vite-plugin-blocks`, `packages/eslint-plugin-blocks` are `packages/yield`, `packages/vite-plugin-yield`, `packages/eslint-plugin-yield`; the twins `examples/*-blocks(-h)` are `examples/*-yield(-h)`; `scripts/blocks-gate.mjs`, `blocks-library.md` and `blocks-gate-baseline.*` are `scripts/yield-gate.mjs`, `yield-library.md` and `yield-gate-baseline.*`; a "block" (the unit) is a routine, a "block component" a yield component, "generator blocks" / "the blocks model" yield components / the yield dialect; the refusal codes `BLOCKS_YIELD_IN_REF` etc. lost their prefix (`YIELD_IN_REF`); `BlockSetter` / `BlockStoreSetter` / `RowBlock` are `Setter` / `StoreSetter` / `RowRoutine`. Since D-096's amendment, `$component` is `component` (entries before it keep `$component`).

## Entries

### D-001 — Destination: standalone npm packages

**Decided.** `@solidjs/blocks` and its companions ship as their own packages, not as a pull request against `solidjs/solid`.
_Alternatives:_ a PR to `solid` adding the packages to the monorepo; keeping the work only on a fork branch.
_Reasoning:_ the library is a userland counterpart of `experiment/iterable-signals` (which bakes the same model into compiler/core). Shipping it standalone keeps the two routes independently evaluable and avoids coupling a design-lab artifact to Solid's release train. Consequences: D-004 (public API only, so the packages can live outside the repo) and Phase 3 (extraction).

### D-002 — Audience: Dev as designer

**Decided.** The audience is Dev designing the model, not end users. Rigor (strict types, exhaustive dev errors, parity tests, a decision log) over polish (docs for newcomers, ergonomics).
_Alternatives:_ a user-facing library with onboarding docs first.
_Reasoning:_ the point of the build-out is to find out whether the model holds up; every ambiguity surfaced is a finding. README should say "this is the strict dialect; the compiler route is the ergonomic one" (design review).

### D-003 — JSX rule as our own Babel/Vite plugin

**Decided.** The one JSX-transform rule (`yield* e` inside a JSX expression/attribute in a generator → `perform(e)` from `blocksModule`) ships as a small standalone plugin (`vite-plugin-solid-blocks`, Phase 2) with no dependency on `@solidjs/compiler`/`@solidjs/babel-plugin` carrying it.
_Alternatives:_ keep the rule in the Rust compiler and babel-plugin (where it is at baseline); require the compiler route.
_Reasoning:_ D-001 — a standalone package cannot depend on an unreleased upstream transform. The Rust implementation stays as the oracle for fixture parity. _Status:_ decided; implementation is Phase 2.

_Implemented (Phase 2, `bl/plugin`)._ The package is `packages/vite-plugin-blocks`, named `@solidjs/vite-plugin-blocks` in the repo and `vite-plugin-solid-blocks` at extraction. Its only runtime dependencies are `@babel/core` and `magic-string`; `@solidjs/blocks` is a peer.

- **The rule** is lifted from the Babel copy into one function, `blocksRule(program)`, which classifies holes and refusals. Two appliers share it: `babelPluginBlocks` rewrites the AST, and `transform(code, { filename, blocksModule })` edits only the rewritten spans, so TypeScript and formatting are kept, the source map is exact, and it returns `null` when nothing changes.
- **The Vite plugin** `blocks()` runs `enforce: "pre"` before `solid()`. It skips a module with no `function*` unparsed, and its map chains through Vite.
- **Commits.** `a6575ff8`: package and fixture parity. `188a99fb`: Vite plugin, source-map test, a no-op over the 683 fixture files of Solid's compilers. `5770f1a5`: twins wired, plus D-047's module-URL pass. `013d20ce`: D-043.

### D-004 — Solid PUBLIC API only

**Decided, hard rule.** The runtime uses only exported, documented Solid 2 API. Anything the model needs that the public API cannot express is recorded in `blocks-library.md` §7 (Limitations) rather than reached for through internals.
_Alternatives:_ patching core; importing from internal paths.
_Reasoning:_ D-001 and D-016 — the packages must survive Solid's RC churn with the twins' parity tests as the only canary.
_Breach fixed by D-095 (review I-3):_ `solid-blocks/h` copied `@solidjs/h`'s internal element brand onto its output, and `render` / the boundaries recognised element thunks by its description (`"hyper-element"`). The library now marks its own output (`ELEMENT_MARK`), and a raw `@solidjs/h` thunk is not a root (a rule in §7).

### D-005 — One way per thing

**Decided.** Aliases and overloads are removed rather than kept for convenience (examples: D-013 removes `$`/`$scope`; D-014 removes the `$optimistic` overload).
_Alternatives:_ keep aliases as sugar with a lint preferring one form.
_Reasoning:_ D-002 — in a design lab a second spelling hides whether the first is sufficient.

### D-006 — Maximal strictness; no escape hatches

**Decided.** No `read()`/`accessor()`/`paths()` escape hatches: every read and write in a block is a `yield*`. (The typed-failures v2 rewrite already removed them — see `.changeset/blocks-typed-failures-v2.md`.)
_Alternatives:_ keep an escape hatch for interop, lint-gated.
_Reasoning:_ the model's claim is that the generator protocol is complete; an escape hatch makes the claim untestable. Interop with plain Solid goes through `adopt()` and `context()` instead.

### D-007 — Baseline is `dfe692cf`

**Decided.** Dev's tip `dfe692cf` ("up", on top of "wip" `57d05dda`) is the baseline. Its unexplained intent was inferred from the diff and recorded in `.changeset/blocks-typed-failures-v2.md` and `blocks-library.md` §10 rather than reverted or re-derived.
_Alternatives:_ baseline at the last documented commit `55f3c695` and re-apply.
_Reasoning:_ the rewrite is coherent (typed failures v2) and the twins pass on it; recording intent is cheaper and more faithful than reconstruction. (Reconstructed note: this is also the baseline this file was rebuilt on after the container loss.)

### D-008 — Gate per commit

**Decided.** Every commit on a topic branch passes `scripts/blocks-gate.mjs`: for each of the 12 twins `test`, `typecheck`, `lint` (and `link:check` until Phase 1B removes it); `@solidjs/blocks` unit + type tests; `@solidjs/eslint-plugin-blocks` and `@solidjs/blocks-linker` tests; prettier check. ~~Chromium/Playwright steps run only before pushes.~~ (Dropped by D-037: no browser test exists.) "Green" = no step red that was green in the reference baseline run (see `blocks-gate-baseline.md`); pre-existing reds are listed there by name. _Reference run (reconstructed baseline, 2026-10-04, `09fa9de5`):_ 52 pass / 2 fail / 1 skip over 55 steps; the reds are `pkg:blocks-linker:test` (3 staleness tests, fixture drift) and `pkg:compiler:test` (1 `blocks-summary` test not updated for `handler_fails` in `dfe692cf`), both pre-existing at the baseline and moot under D-023; `repo:oxlint` is SKIP (binary not installed). The babel-plugin and compiler steps run vitest only, against the already-built artifacts (the gate never builds). The timezone pin is D-027.
_Alternatives:_ repo-wide `pnpm test` (too slow, and unrelated reds); gate only at merge.
_Reasoning:_ the twins' DOM-parity tests are the model's only semantic oracle (D-016); running them per commit is what makes "ff when green" (D-009) meaningful. Build `@solidjs/blocks` with `--force` before gating — twins resolve it via `dist/`, and an unforced filtered build has produced spurious reds.

### D-009 — Branching and commit discipline

**Decided.** Topic branches `bl/<topic>` (branch names `blocks-lib/<x>` are impossible because `blocks-lib` exists as a branch). Conventional commits; one changeset per user-visible change; fast-forward into `blocks-lib` when the gate is green. Forks of a topic are logged in this file. Agent commits are authored `Claude <noreply@anthropic.com>`.
_Alternatives:_ commit directly on `blocks-lib`; merge commits.
_Reasoning:_ keeps `blocks-lib` linear and every commit gated, so bisecting a twin regression is one `git bisect` away.

### D-010 — Order of work

**Decided.** Phase 1A tighten (runtime/type hardening on the current repo) → Phase 1B declared prop colors → Phase 2 standalone plugin → Phase 3 extract to its own repo → Phase 4 extend.
_Alternatives:_ extract first, then tighten in the new repo.
_Reasoning:_ tightening needs the in-repo twins, the Rust compiler as oracle and the full Solid test infrastructure; extraction before that would duplicate all three. Phase 2 is file-disjoint from 1B and may run in parallel (Q23).

### D-012 — No-JSX flavor is first-class

**Decided.** The `h`/`html` flavor (`@solidjs/blocks/h`, `/html`) is first-class: same hole forms as JSX, same strictness, its own twins (`*-blocks-h`), and it must be a no-op for the JSX plugin.
_Alternatives:_ JSX only; no-JSX as a best-effort subset.
_Reasoning:_ the no-JSX flavor is the proof that the model does not depend on the transform (D-003): whatever JSX can express via the rule, `h` expresses without it. _Amended by D-046:_ the flavor is `h()` only; the `html`` ` tagged template is dropped.

### D-013 — Rows and holes are bare `function*`

**Decided.** A row (list item body) or a hole (a reactive child/attribute position) is a zero-arity generator function; the runtime wraps it (as `holes.ts` `toHole` does). The `$` and `$scope` helpers are removed (lint `no-dollar-block` with autofix first; the rule stays as a deprecated-usage rule). A derivation reused in several holes is a `yield* $memo`.
_Alternatives:_ keep `$` as the explicit marker; keep `$scope` for shared derivations.
_Reasoning:_ D-005 — `$` was a second spelling of "this is a block"; `$scope` was a second spelling of `$memo`. Migration size at decision time: 33 twin sites + 14 test sites. _Implementation:_ Phase 1A item 4.

### D-014 — `$optimistic` / `$optimisticStore` symmetry

**Decided.** `$optimistic` is the scalar form and `$optimisticStore` the object-or-body form, mirroring `$signal` / `$store`; the overload of `$optimistic` that accepted a body is removed. `context()`, `$snapshot` and `start` are kept as they are.
_Alternatives:_ merge everything into one `$optimistic`; remove `context()` in favour of `createContext()`.
_Reasoning:_ D-005 and symmetry with the existing pair. Whether `context()` and `createContext()` stay separate long-term is deferred until after Phase 1B. _Implementation:_ Phase 1A item 5.

### D-032 — A view has no body

**Decided (Dev, 2026-10-04).** A view is `function* () { return <…/>; }`. Every read is a `yield*` directly in a JSX position (a hole); there is no `yield*` outside JSX, no `if`/early `return`, no local computation. All structure comes from flow controls (`<Show>`, `<Match>`, `<For>`, …), which take sources directly. The `h`/`html` flavor follows the same rule with explicit `function*` holes.
Consequences: (1) the whole-view read concept is deleted — `VY` is always `never`, so `ViewPending<VY, R>` collapses to `PendingOf<HOps<R>>`; a view is never pending or failing on its own, only its holes are; the runtime's whole-view detection (`viewRunning`/`jsxRead`, the machinery `a5faef57` patched) is repurposed into a dev error and otherwise removed (1A item 3 shrinks accordingly). (2) Enforcement at three levels: types (`Read` is not a `ViewOp`; type test "a view does not read"), dev runtime (`[READ_IN_VIEW] <Component>: read outside a JSX position`), lint `no-read-in-view-body` (error, in `recommended`). (3) Doc §3 row "A view reads; it does not create or write" becomes "A view does not read, create, write or branch; its holes read". (4) Twins migrate view-body reads and `if (yield* …)` branches (6 by grep) to holes and flow controls; the lint's first run gives the exact site count, which is recorded here.
_Alternatives:_ keep whole-view reads and document the position-based granularity (§3 only); lint only the cliff case (a view-body read whose binding is used only in JSX); keep whole-view reads in the runtime for safety.
_Reasoning:_ Dev: there should be no control flow or structure inside a view; all branching comes from flow controls, and a read is a hole. This removes the cliff (the same `yield* count` meaning a hole inside JSX and a whole-view re-render one line above) by removing the second meaning, not by warning about it. Fact that settled it: `ViewPending<VY, R> = PendingOf<VY | HOps<R>>` — holes were already tracked for pending/failures, so the whole-view read bought nothing but structure and a coarser scope. _Implementation:_ new Phase 1A item 4b, after explicit holes (item 4).

### D-034 — Error types carry a literal `kind`

**Decided (Dev, 2026-10-04).** `attempt`/`until`/`raise`/`<Errored catch>` remove a handled class from a failure union _structurally_ (TS compares shapes) but match at runtime with `instanceof` (nominal). Two classes without a discriminant are one type to TS, so `catch={[A]}` would also erase `B` from the type while the runtime rethrows `B`. The types now enforce the convention every twin already follows: an error type accepted anywhere as `E` must satisfy one shared constraint `Failure = Error & { readonly kind: <string literal> }` (a plain `string` `kind`, or none, fails with a branded-never message: "error class X needs `readonly kind = \"x\" as const` so its failure can be told apart"). Entry points: `attempt<T, E>`, `until<T, E>`, `raise<E>` (unconstrained before this), `Errored`'s `catch`, and `Async<T, E>` in Phase 1B; everything else inherits.

_Reasoning:_ a typed-failure system whose type-level removal and runtime matching can disagree is unsound in exactly the case it exists for; the constraint costs one line per error class, which every twin already pays. _Implementation:_ Phase 1A, with item 7; type test for the two-identical-classes case.

### D-040 — `Async<T, E>` on a prop is permission only

### D-048 — `$event` paused on a pending read

**Decided (Dev, 2026-10-04): `$event(body, { latest: true })`.** A read inside an event that hits a pending source waits for its data (tested); the wait is unbounded (only `until` has a timeout) and by default a second call of the same event starts another independent run while the first keeps waiting. Nested event calls already merge into the outer transaction (Solid's `action`: "a nested action … runs inside the OUTER action's slice"). With `latest: true`, a new call closes the earlier run that is still paused (or awaiting an async `attempt`) — the runtime already closes superseded generators with `gen.return()` in the memo and event paths — and the closed run's promise settles as superseded (not a failure; the event's typed-failure color is unchanged). Runtime test: typing fast into a search box — only the last call's writes land. Doc §1 events bullet.
_Alternatives:_ independent runs only (document); a per-event `timeout` failing with a typed `TimeoutError`.
_Reasoning:_ the search-box case is common and the mechanism exists; an opt-in keeps Solid's default action semantics. _Implementation:_ Phase 1A item 8 (touches the event path).

### D-050 — D-013 amended: in JSX the hole is `yield*` only

**Decided (Dev, 2026-10-04, from a Phase 1A finding).** A bare `function*` as a JSX child or attribute value cannot be a hole: the JSX compiler passes it straight to `@solidjs/web`'s `insert()`/`setAttribute()`, which never call the library. In JSX the hole form is `{yield* x}` (the transform's `perform`); a `function*` block is the `h` flavor's hole form and the form for flow-control **props** (`<Show when={function* () { … }}>` reaches the component, D-038). A `function*` JSX child/attribute is a type error, pinned by a type test.
_Alternatives:_ a second transform rule rewriting a `function*` JSX child/attribute into a hole call — rejected, it reverses D-031's one-rule stance.
_Reasoning:_ the transform is the ergonomic path (D-031); the one thing it rewrites is `yield*`. Implemented in `9f0dac54` on `bl/tighten`.

### D-051 — D-032 amended: JSX enforcement is runtime + lint

**Decided (Dev, 2026-10-04, from a Phase 1A finding).** At the type level a JSX view's hole reads _are_ its yields — TypeScript types `{yield* user.name}` inside JSX exactly like a statement yield — and that is the only channel for a JSX view's colors (`ViewPending<VY, R> = PendingOf<VY | HOps<R>>`). So "`Read` is not a `ViewOp`" holds for `h` (`HViewOp = never`, `[HVIEW_READ]`) but cannot for JSX. For JSX the no-body rule is enforced by the dev error `[READ_IN_VIEW]` and the lint `no-read-in-view-body` (which replaces `no-read-outside-hole`, D-005); migration count on the lint's first run: 0 in every twin (the old rule already enforced it). Recorded in §7 as a limitation of the transform route.
_Alternatives:_ time-boxed research into branding `perform`'s yield (`HoleRead`) so a statement-level `Read` is rejected while JSX reads pass.
_Reasoning:_ no parity test failed and the rule is enforced at two of three levels; a type-level form for JSX may not be expressible in TS. Implemented in `b1634e33` on `bl/tighten`.

### D-062 — Components are called, not tagged

Props are a plain object literal, checked directly against the declared prop type (D-056). Enforcement: lint `no-component-tag` (error, `recommended`) with an autofix tag → call; the JSX namespace rejects component tags at the type level if feasible; twins migrated (every component tag). _Alternatives:_ tags erase colors by rule (runtime propagates; §7 limitation); decide from 1B's counts.

### D-065 — Call-form props take a source, a hole or a settled value

**Decided (Dev, 2026-10-04; D-062 rule 1).** A JSX tag wraps each dynamic attribute in a getter, so the read happens inside the child; a call evaluates its arguments first, in the parent — `Show({ when: (yield* n) > 0 })` would read in the parent's hole and re-create `Show` and its subtree on every change. So a prop value in call form is a `Source`, a zero-arity `function*` hole (D-038 generalised from flow controls to every component prop: `Card({ total: function* () { return (yield* n) * 2; } })`), or a plain settled value; the child reads it with `yield*` like any prop (D-042). A `yield*` inside a call's argument is a lint error: `no-read-in-prop` ("read in a prop: pass the source, or a hole").
_Alternatives:_ a named `$memo` per derived prop in the caller's setup.
_Reasoning:_ D-038 and D-042 made consistent — everything a component is given is reactive, and derived values have one form everywhere.

### D-066 — A component call's `children` is always a generator

**Decided (Dev, 2026-10-04; D-062 rule 2).** A tag builds its children inside the parent component — after it set its context, or decided to show them; a call would build plain-JSX children eagerly in the caller (`IdentityProvider({ children: <Router/> })` builds the router and its `useIdentity()` consumers before the provider sets its context; `Show({ children: <Panel/> })` builds while hidden). So `children` in call form is always a generator: `children: function* () { return <p>{yield* x}</p>; }` — a lazy view that may contain holes; lists take `children: function* (item, index)` rows (D-055). There is no plain-JSX children form; arrow render callbacks become row generators.
_Alternatives:_ allow plain JSX children when they contain no holes (two forms, and the provider case still builds eagerly).
_Reasoning:_ one form, always lazy — what the tag did implicitly; the verbosity is the cost of call form.

_Typed by D-094:_ for the library's flow controls and boundaries a JSX element as `children` (or `fallback`) is a type error, `[LAZY_VIEW]`; the lint stays as the autofix.

### D-067 — Tags are DOM elements and foreign Solid components; block components are called

**Decided (Dev, 2026-10-04; D-062 rule 3).** Solid's own components (`Router`, `Portal`, `HydrationScript`, context providers, Solid's `Reveal` — 11 twin sites) return Solid's `JSX.Element` and need Solid-style lazy props, so `yield*` cannot take them. Rule: a JSX tag is for things that are not blocks — DOM elements and foreign (plain-Solid) components; a block component is called. _Reasoning:_ it states the real boundary — the model vs plain Solid — instead of hiding it behind a bridge or wrappers that grow with every foreign component. ### D-070 — Raise at every host: where a failure is typed, where it lands

**Recorded (Phase 4, item 2; for Dev's ruling).** `packages/blocks/test/raise.spec.tsx` raises a kinded failure in every host and checks where it goes. The hosts: a setup; a hole (a prop's, and a flow control's source); a `$memo` (before and after an async `attempt`); an `$effect`; a `$settled`; an `$event`; a row. `raise.type-tests.tsx` pins `FailsOf` at each position. The suite runs on development and production builds.

At run time every host behaves as D-033 says:

- The failure reaches the nearest `Errored` as the original instance.
- An `Errored` whose `catch` does not list it passes it to the one above.
- With no `Errored` it is re-thrown at the root.

**How it is re-thrown depends on the host** (pinned, Solid's behaviour):

- a setup throws the failure itself out of `render`;
- a computation (a hole, a memo, an effect, `$settled`, a row) re-throws Solid's own error, with the failure as its `cause`;
- a memo failing after an async step becomes an unhandled rejection of that error;
- an event's call rejects with the failure, so a DOM dispatch with no boundary leaves an unhandled rejection.

A root handler that wants the typed failure reads `error.cause ?? error`.

**Where the failure lands in the types:**

| Host                           | `FailsOf`                                                                                                  | Lands in the component's view type?                 |
| ------------------------------ | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| setup                          | refused: `Raise` is not a `SetupOp` (a setup never reads, so it has nothing to fail on)                    | —                                                   |
| hole (a prop's)                | the child's view, through the prop's declared `Source<T, E>`; a raising hole is refused for a settled prop | yes                                                 |
| hole (a flow control's source) | the flow control's output                                                                                  | yes                                                 |
| `$memo`                        | `Source<T, E>`                                                                                             | yes, through the holes that read it                 |
| row                            | the flow control's output (D-059)                                                                          | yes                                                 |
| `$event`                       | `EventHandler<Args, E, …>`; `yield* go()` in another event joins it                                        | **no**: `onClick={go}` takes the handler as a value |
| `$effect` / `$settled`         | **dropped**: both give `Yieldable<Create<…>, void>`                                                        | **no**                                              |

- **F1 (open): an effect's failure is in no type.** A component whose `$effect` or `$settled` raises has the view type `View<false, never>`, yet it fails at run time, to the nearest `Errored` or re-thrown. §1 says "typed failures are complete for library-mediated failures", and this is one that is not. Options:
  - carry the body's `FailsOf` into the setup's yield union (`Create<"effect", E>`) and into the view's colors, the way a memo's failures reach the holes that read it;
  - refuse `Raise` in an effect (`EffectOp` without `Raise`), so an effect's fallible work goes through an event or a memo;
  - accept it and say so in §7.
- **F2 (open): a DOM-dispatched event's failure is in no view type.** A DOM dispatch ignores the returned promise, so the failure goes to the nearest `Errored` (documented on `$event`). The handler's type carries `E`; the view that binds it with `onClick` does not. Options:
  - join an event's `E` into the view when it is bound in a JSX event position, which needs the JSX namespace to read the handler's type;
  - require a handler bound to the DOM to have `E = never`, so failures are handled inside it (`attempt`, or an `$optimistic` rollback);
  - accept it and say so in §7.
- **F3 (fixed): a hole that always raises lost its failure.** `GeneratorOps<Y, R>` in `holes.ts` distributed over the hole's return type. A hole that always raises returns `never`, so the whole result was `never` and its own `Raise` was dropped. `Show({ when: function* () { return yield* raise(e); } })` typed as settled and never failing. `never` is now its own case. The type test is "a flow control's source hole" and the changeset is `blocks-raising-hole-type.md`.

### D-071 — Meta-rule: colors are sound upper bounds on runtime routes

**Decided (Dev, 2026-10-05; clarified by D-112).** Colors are sound upper bounds, not proofs that a route executes. No discharge may erase a route the runtime can take. Wherever the runtime routes a color — pending, a failure — the type carries it to the same place. A channel the runtime has and the type lacks is a bug, never a §7 limitation. D-034, D-044, D-047, D-059, D-063, D-072, D-073 and D-074 are instances. A future finding of the form "the runtime does X but the type says Y" is resolved by making the type say X. A finding where the type cannot say X is reported to Dev; it is not documented away.
_Consequence._ §7's "two library-mediated failures are in no view type (open, D-070)" is not a limitation: D-070 F2 is ruled by D-072 and F1 by D-073.
_Instance (2026-10-06, calculus §6.3 F-1)._ `Errored`'s call form carried only a lazy view's and a row's fallback colors. A render function `(error, reset) => …`'s output and `h` output were dropped, though the runtime sends their pending reads and failures to the boundaries above and `h(Errored, …)` carried them. Every fallback form now carries its colors (`Ops<F>`, as `Loading`'s fallback). `h`'s boundary overloads match a phantom `[BOUNDARY_KIND]` rather than `typeof Loading` / `typeof Errored`: with the colors carried, comparing the two overload sets was TS2589 ("excessively deep") in the `h` twins. Type tests for each form (raise.type-tests); runtime tests that each form's failure reaches the `Errored` above, and an `h` fallback's pending the `Loading` above (obligations.spec, O28 / O29).

### D-072 — Binding an event in a view is a hole (D-070 F2)

**Decided (Dev, 2026-10-05).** `<button onClick={yield* save}>` yields a **Bind** op. It contributes the handler's failures (`FailsOf`) and its `P` (`ReadsPendingOf`: it may wait on a pending read) to the enclosing view's type, and evaluates to the handler unchanged. The runtime binds it as before: a failure nobody handles goes to the nearest `Errored` above the handler's creation site (D-019, D-033). _(Amended by D-085: the bind site's.)_ `yield* save` (bind) is distinct from `yield* save(x)` (call): bind is the un-called `EventCall` handler.

- The transform's refusal in event positions, `BLOCKS_YIELD_IN_EVENT`, moves to the types. `perform(save)` in an `on*` attribute is allowed when the expression is a block event handler (a type-level check); a source or any non-handler there is a type error. `ref` stays refused.
- A plain `onClick={save}` (no `yield*`) is the lint error `no-unbound-event`; its autofix adds the `yield*`.
- Migrated under this decision: the 8 twins, the package tests, the conformance scenarios, getting-started and refusals.md (site counts below, with the implementation).

_Implemented (Phase 5, commit 3: the mechanism)._

- **Types.** `Bind<P, E>` is a new op, a `ViewOp` (not an `EventOp`, a `MemoOp`, a `HoleOp` or a hole prop's). `EventHandler` is iterable: `[Symbol.iterator](): Generator<Bind<P, E>, BoundEvent<Args>, any>`, where `BoundEvent<Args>` is the handler's call signature with a `[BOUND]` brand (`Bound<H>` brands a DOM handler type). `PendingOf` / `FailsOf` read `Bind` as they read any op, so a bound event's `P` makes the view pending and its failures join the view's. _(Superseded by D-075 as amended: a bound event's `P` no longer makes the view pending; it is the view's may-wait marker.)_ `A` (async work of its own) does not: a view does not wait for a call. In `h`, `OpsOfHole` maps an `$event` handler given as an attribute to `Bind<P, E>`.
- **Runtime.** A handler is marked (`EVENT_MARK`) and iterable: `yield* save` returns it. `perform` returns a marked handler as it is (it called any other function). Nothing else changes: the DOM calls the handler, and a failure nobody handles goes to the `Errored` above the creation site.
- **Transform.** `BLOCKS_YIELD_IN_EVENT` is removed from the rule, its `REFUSALS`, its d.ts and the lint's `yield-in-jsx-hole`. The three refused cases of `rule.json` are accepted cases now (#7–#9), plus the bound-data array (#10). Their compiled outputs were generated by `generate.mjs`; the other 26 outputs were byte-identical. Solid's compiler evaluates `onClick={_$perform(save)}` once, as the element is created (`addEvent(el, "click", _$perform(save), true)`, or `$$click` / `$$clickData` for the array form), drops it on the server, and makes it a getter on a foreign component's props.
- **Lint.** `no-unbound-event`: an event prop (`onX`, `on:x`, `oncapture:x`) whose value, or whose array's first element, is an `$event` handler and not a `yield*`. With type information a handler is anything with the library's `[EVENT]` brand (so `onInput={pick("a")}` is reported); without it, a binding of `$event(…)`. The autofix inserts `yield* ` in a generator.
- **Staging.** In this commit the JSX namespace's event attributes still take an unbound handler and `recommended` leaves `no-unbound-event` out, so the gate stays green before the migration. The next commit makes both refusals and migrates every site.

_Implemented (Phase 5, commit 4: the refusal and the migration)._

- **The refusal.** `scripts/jsx-web-shared.mjs` rewrites the vendored namespace's `EventHandlerUnion` to `Bound<EHandler> | BoundEventHandler<…>`, whose element 0 is `Bound<…>` too. An event attribute takes only a bound handler; an unbound `$event` handler, a plain function and a value read from a source (a prop holding a handler or a function) are type errors ("Property '[BOUND]' is missing"). In `h`, a plain function in an event attribute is refused the same way (an `$event` handler is the bind there). `no-unbound-event` is in `recommended`, as an error.
- **`Errored`'s `reset`** is Solid's: it re-renders the children and cannot pend or fail. It is typed `Reset = BoundEvent<[]>`, already bound with no colors, so `onClick={reset}` stays as written (3 JSX sites, 1 `h` site).
- **`Errored`'s fallback (a D-071 gap found on the way).** Its colors were dropped from the output type although the runtime sends a fallback's pending reads and failures to the boundaries above. A lazy-view fallback's colors now join the output, and a row fallback `function* (error: Path<E>, reset: Reset)` is typed (the runtime already ran one). TypeScript does not infer a generator fallback's parameters (a limitation of overload inference, bisected: it holds even for `For`'s own row signature in a `declare function`), so they are annotated. The overloads are per form (row; lazy view or content or render function). A generic fallback parameter constrained by the recursive `Content` type made `h(Errored, …)` "excessively deep".
- **One twin type was wrong.** effect-blocks' `effectAction` typed its call `EventCall<R, unknown, boolean, true>`: `P` widened to `boolean`, though the saga driver reads no pending source. Binding `place`, which calls it, made the root pending. It is `false` now (2 lines in `solid-effect.ts`), which is what the runtime does.

### D-073 — An effect's raise joins the component's failure type (D-070 F1)

**Decided (Dev, 2026-10-05).** `$effect` and `$settled` bodies may raise. Their `FailsOf` joins the enclosing component's failure type, unless the effect handles the failure itself (an attempt whose `onError` absorbs it). This is Solid's runtime semantics today: an effect's failure reaches the nearest `Errored` (D-070's matrix). Tests: a type test, and a runtime test that an effect's raise reaches the nearest `Errored`.

_Implemented (Phase 5, commit 2)._

- `Create<K, E = never>` carries a failure. `$effect` and `$settled` give `Create<"effect" | "settled", FailsOf<body>>`; `$component` adds `FailsOf` of its setup's yields to its view's failures, and a row's setup's failures join the flow control's output (`RowOps<VY, R, Y>`; `RowFails<VY, R, Y>`). A memo's `Create` carries none: its failures are its source's.
- **"An attempt whose `onError` absorbs it" did not exist:** every handler's result was thrown. It is now: a handler returning a value that is not an `Error` absorbs the failure, and the attempt gives that value (types: a second overload of `attempt`, no `Raise`; runtime: `handled()` in the attempt and in `mapStream`). A stream's absorbed failure ends the stream, so the absorbed value is not in the attempt's type there. A handler that may return either is `[ATTEMPT_ABSORBS]`. _(Replaced by D-076: an absorbing handler returns nothing, and the attempt gives `undefined`.)_
- Not visible to the types: a `try` / `catch` around a `yield*` in a block body (effect-blocks' `place`, room's `drop` and `submit` events) handles a failure at run time while the body's type keeps it. The type over-states there; it never under-states. Recorded, not changed. _(Ruled by D-077: `try` / `catch` is not a block form.)_

### D-075 — A bound handler that may wait is a may-wait marker on the view (types only)

**Decided (Dev, 2026-10-05; amended the same day).** _Ruling as amended: types only._ A bound handler's `P` (its call may wait on a pending read) does **not** make the view pending: the runtime never suspends a view for a waiting call, so a pending view type would over-state the runtime (D-071: no over-statement of discharge, D-112). It is carried instead as a separate **may-wait marker** on the view, folded like `PendingOf` but never joining `ViewPending`, and surfaced by the lint **warning** `no-unshown-wait`: "this view binds a handler that may wait on pending data; show its in-flight state". No runtime support, no automatic `Loading`. Type test: binding a may-wait handler does not make the view pending, and the marker is present.

_The first ruling (superseded)._ An event exposed its in-flight state as a typed source, `save.pending: Source<boolean, never, false>`, `true` while any call was paused on a pending read or awaiting an async attempt. **It was built and reverted:** Phase 5 commit 5 (`8b6ab6b`: the source in the runtime, its runtime and type tests, getting-started §6) was undone by `git revert`. The stop-report that led to the amendment: D-072's bound `P` made the view pending although the runtime never suspends a view for a call.

_Implemented (Phase 5 amendments, commit 2)._

- **Types.** A phantom `[MAY_WAIT]`. `Bind<W, E>` carries the handler's `P` there instead of in `[PENDING]`, so `PendingOf` does not see it. `MayWaitOf<Y>` folds it like `PendingOf` (a `Bind`, or a child view that may wait). Views carry it as a third parameter, `View<P, E, W>` (`ComponentView`, `Component`, `HView`, `ChildView`), defaulting to `boolean`: it is not a color, so every annotation without it accepts either, and a may-wait settled view is an element. `$component` gives `ViewMayWait<VY, R>`; flow controls and boundaries (`Loading` and `Errored` included: neither handles it), `h` and `lazy` pass it on. The element type's view members omit the key, so a view returning an element does not read the element type itself as a child that may wait. `EventHandler` has `[MAY_WAIT]?: P` for the lint.
- **Lint.** `no-unshown-wait` (a warning in `recommended`; type information only, silent without it): an event attribute bound with `yield*` (or the first element of the bound-data array), or an `h` `on…` attribute, whose handler's `[MAY_WAIT]` may be `true`.
- **Where it fires.** 7 bind sites in the twins, all left as warnings: todos-blocks `retry`, `toggle`, `clear`; todos-blocks-h the same three; room-blocks `submit`. The originals show no in-flight state there, and the twins keep parity. No twin's `Loading` became unnecessary for the type: those views were pending through their own reads too.
- **Tests.** raise.type-tests "an event that may wait … does not make the view binding it pending" (the view is settled and an element; the marker through `Show`'s content and a child view; `h`); rules.test.js `no-unshown-wait` (with types: `true`, `boolean`, the bound-data form, `h`; without: silent).

_Note (2026-10-06, a first-time-user review, log item 9): `Handler<Args, E = never>`_ is `EventHandler<Args, E, unknown, false, boolean>`, the type to declare an event prop with. `EventHandler`'s defaults (`P = boolean`) read as "may wait", so a prop declared `EventHandler<[Theme]>` made `no-unshown-wait` fire on a handler that only calls a setter; spelling the colors out took five positional arguments. `Handler` is an alias, not a rule change: a handler that may wait on pending data is still declared `EventHandler<Args, E, unknown, true>`. The review also noted that an event waiting on its own async work (`A`) is not flagged by `no-unshown-wait` while one reading pending data (`P`) is; that is D-075's rule as written (the marker is `P`), recorded here, not changed.

### D-076 — An attempt's handler returns the failure, or nothing

**Decided (Dev, 2026-10-05); amended by D-078** (a handler may be a generator, and a returned value absorbs with that value: "a non-`Error` value is a type error" is withdrawn; "return nothing to absorb" holds). Replaces D-073's two-overload `Absorbs<V>` scheme. `onError` returns either an `Error` with a literal `kind` — the failure, possibly transformed from `unknown` or from a call's known failure — which the block fails with, or nothing (`void`): the failure is absorbed, the attempt yields `undefined`, and its result type is `T | undefined`. Returning a non-`Error` value is a type error. A handler typed `E | void` stays refused as `[ATTEMPT_ABSORBS]`, reworded: "a handler returns the failure (an Error with a literal kind) or nothing (absorbs it), not sometimes one and sometimes the other". Absorbing a stream's failure still ends the stream. Absorbing handlers that returned a value migrate (`??` for a fallback). Docs: §1 and refusals.md.

_Implemented (Phase 5 amendments, commit 3)._

### D-078 — An attempt's handler may be a generator (amends D-076)

**Decided (Dev, 2026-10-05).** `attempt(fn, handler)` with `handler: (error) => Error | void | Generator<HostOps, Error | V>`.

1. One handler, decided by its result: if it returns a generator, it runs as block code; otherwise its return is interpreted directly. A plain `e => new SendError(e)` is the degenerate form.
2. The generator's ops are the **host's** (an event: reads, writes, async, a nested attempt; a memo: reads, `raise`, a nested attempt; an effect: synchronous only), and its colors (`P`, `E`, `A`) join the host's. It is not a new host and has no boundary semantics. `yield* raise(e)` inside it fails the attempt with `e`. Type: `AttemptOps` folds the handler generator's yields.
3. The return decides the outcome: an `Error` with a literal `kind` (`KindCheck`) → the attempt **fails** with it (a transform; the only way a failure leaves the handler); nothing → **absorbed**, the attempt yields `undefined` (`T | undefined`); a value `V` (a nested attempt's result) → **absorbed**, the attempt yields it (`T | V`). A handler typed to return an `Error` sometimes and sometimes not → `[ATTEMPT_ABSORBS]`, reworded. D-076's "a non-`Error` value is a type error" is withdrawn; "return nothing to absorb" holds.
4. When it runs: synchronously for a synchronous throw; on rejection for a promise, inside the event's transaction (as an attempt already re-enters it) or as the memo's resumption; per failure for a stream — an `Error` fails the stream, anything else ends it. It runs under the same `runAs` host as the attempt (receipt tracking, `UNTYPED_THROW`, `READ_IN_VIEW` apply).
   _Amended by D-091:_ a stream attempt's handler is a plain function (an `Error` fails the stream, nothing ends it); a generator there is a type error and `STREAM_HANDLER` at run time; an `$event` does not attempt a stream.
   Tests: type tests for each return shape and for host-op admission (a write in a memo's handler is a type error); runtime tests: transform, absorb with nothing, absorb with a value, a nested attempt (retry / fallback), `raise` inside the handler, a handler's write inside an event's transaction, a stream's end vs failure. Docs: §1, refusals.md, getting-started (the retry example). Migrate nothing unless a twin benefits. `until`'s handler follows the same rule (Dev, on the Phase 5 report).

_Implemented (Phase 5 amendments, commit 6)._ Not a revert of D-076: its commit stands, amended by this one.

- **Runtime.** `handle(onError, e)`, a generator the `Attempt` delegates to (`yield*`) wherever it caught a failure — a synchronous throw, an event call's failure (D-077), a rejection: the handler's result, when it is a generator object, is delegated to as part of the attempt, so its ops reach the host's driver (an event's `eventSteps`, inside the transaction; a memo's resumption; an effect's synchronous `drive`, which refuses a wait). Its return: an `Error` is thrown (`known`), anything else is the attempt's value. A stream's failures happen outside the attempt's run: the handler runs under `runAs` with the attempt's host and name (as a resumption), a generator `drive`n synchronously; an `Error` fails the stream, anything else ends it.
- **Types.** `attempt<T, H>(fn, onError: (error: Caught<T>) => H & HandlerCheck<H>)`, no constraint on `H`. `HandlerReturn<H>` (a generator's return, else `H`), `HandlerYields<H>`; `AttemptOps` = the wait, the handler's yields, and `Raise<R>` when `R` is an `Error`; `AttemptResult` = `Attempted<T>`, or with `undefined` / `V` when absorbed. `until` gives `AttemptOps<Promise<T>, H>` / `AttemptResult<Promise<T>, H>`.
- **Twins.** None migrated. room's `post` and `drop` (D-077) record a failure for the UI through a closure; a generator handler could write it directly (`function* (cause) { yield* setError(new SendError(cause).message); }`), which reads better but is not a behaviour change; left as is (report).
- **Docs.** §1's `attempt` bullet, refusals.md (`[ATTEMPT_ABSORBS]`, a host op the handler's host does not take), getting-started §3 (the retry; its program and spec too).

### D-079 — `$effect` is split: `$effect(compute, effect)`

**Decided (Dev, 2026-10-05).** `$effect(compute, effect)`, both generators, its runtime semantics mirrored at the type level; supersedes D-053's one-pass form (`$settled` stays as is: `onSettled`, not a tracked effect). The one-function form existed so a compiler could split it statically; that cannot happen at run time, so the split is written by hand now. A compiler-only ergonomic wrapper (e.g. `$hoistedEffect`) may reintroduce the merged form later. No `createTrackedEffect` (legacy): Solid's `createEffect(compute, effect)`.

- **compute**, `function* ()`: tracked reads (`Read` ops), `raise` (D-073), a sync `attempt`; pure — a `Write` or a `$cleanup` here is a type error; returns a value `V`.
- **effect**, `function* (value: V, prev: V | undefined)`: runs after the compute, untracked: `Write`, `$cleanup`, a sync `attempt`, a sync event call, `$untrack`. A plain `yield* <source>` here is a type error ("read it in compute and pass the value, or `$untrack` it"), mirroring Solid's untracked effect phase.
- D-073's raise-joins-component applies to the compute; an effect-phase raise is a component failure too (the same runtime path): both are typed.
- Migrate every `$effect` in the package tests, the 8 twins, the scenarios and the docs (report the counts). Re-record the blocks-effect golden: D-069 F1 should disappear; a remaining difference is a new finding.

_Implemented (Phase 5 amendments, commit 7)._

- **Runtime.** `createEffect(compute, { effect, error }, options)`. The compute runs as a new host, `COMPUTE` ("an effect's compute": `WRITE_IN_REACTIVE` for a write, `CLEANUP_OUTSIDE_OWNER` for a `$cleanup`, `ASYNC_NOT_ALLOWED` for a wait). The effect phase runs as `EFFECT` with a cleanup sink (returned to Solid: it runs before the next effect run, or on disposal); a plain read there is the new development error `READ_IN_EFFECT`, an `$untrack` is not. `$settled` has its own host, `SETTLED`, with `$effect`'s old rules (reads allowed). **Solid logs and skips a compute failure** unless the effect has an `error` arm, so the arm rethrows it: it then reaches the nearest `Errored`, as an effect-phase failure does (D-073 holds). With no `Errored`, either is thrown out of `render` / `flush` as itself and Solid reports `REACTIVITY_HALTED` (the one-pass effect's was re-thrown wrapped, its `cause` the failure): raise.spec's host table records `thrown` for both phases.
- **Types.** `$effect<YC extends ComputeOp, V, YE extends EffectPhaseOp>(compute, effect: (value: V, prev: V | undefined) => …)` gives `Create<"effect", FailsOf<YC> | FailsOf<YE>>`. `ComputeOp` = `Read | UntrackedRead | Raise`; `EffectPhaseOp` = `UntrackedRead<false> | Write | Cleanup | Raise | EventCallOp<false, false>`. **`$untrack` is its own op now**, `UntrackedRead<P, E>` (it was a `Read`), so the effect phase can take it and refuse a tracked read; every union that admitted `Read` admits it. A refusal now lands on the offending half, not on the `$effect(` call.
- **Lint.** The effect phase (`$effect`'s second argument) is a block for every rule (`no-try-catch`, `no-throw`, `jsx-only-in-view`, …); `no-foreign-reactive` points `createEffect` / `createTrackedEffect` at `$effect(compute, effect)`.
- **Migration: 31 `$effect` sites.** Package tests 28 (runtime.spec 7, raise.spec 7 — its host table's effect case now one case per phase —, raise.type-tests 8, jsx.type-tests 5, nojsx.spec 1), lint test strings 2 (plus one new case for the effect phase), conformance 1 (blocks-effect, written as the reference's split form). **The twins: 0** (none uses `$effect`: their effects are `$settled`, 3 files). Docs: no `$effect` example; prose in §1 / §3 / §7, refusals.md and getting-started updated. The transform's compiled fixtures mention `$effect` only in their frozen twin snapshots (D-043), unchanged.
- **Conformance.** blocks-effect's client/library trace now equals the oracle's: **F1 is gone**, its declaration removed, COVERAGE.md regenerated. No new finding.
- **Tests.** raise.type-tests "D-079" (the compute's value and `prev` typed; a write, a `$cleanup` or an event call in the compute refused; a plain read in the effect phase refused; both halves' failures; the `Create` type); runtime "an $effect's compute does not write; its effect phase does not read (D-079)"; raise.spec both phases.

_Amended by D-083._ The effect phase admits a plain read of a settled source, untracked because the phase is; `READ_IN_EFFECT`, `UntrackedRead` and `$untrack` are gone. The bullets above describe the first implementation.

### D-081 — An `$event` call is one transaction (D-069 F4 is the model)

**Decided (Dev, 2026-10-05).** D-069 F4 is not a divergence to remove: it is the model, D-020's. An `$event` call is one transaction. ### D-084 — On the server a view's holes are read before its children (D-069 F8 is the model)

**Decided (Dev, 2026-10-05).** D-069 F8 is not a divergence to remove: it is the model. A hole is a computation the view owns, and the interpreter resolves a view's computations, then descends into its children. So on the server the library reads a view's holes before it renders the view's children. Handwritten Solid interleaves them in markup order: blocks-row-recursive's oracle reads `open a` for the toggle, renders the nested rows, then reads `open a` again for the `<ul>`'s `style`. The reads, the values and the markup are the same. The difference shows only in a read trace, and only on the server: the client and hydrate traces are equal. No code change. The declaration in `declared.ts` stays as the pin.
_Alternatives (rejected):_ reorder the SSR interpreter so it interleaves hole reads with child rendering.
_Reasoning:_ the difference cannot be observed: same reads, values and markup. The compiler route would not share a reordered interpreter anyway. Reordering would add machinery to the library route to match an order nothing depends on.
_Documented._ §3, next to the D-081 note: "on the server a view's holes are read before its children; the markup is unaffected". D-069's status table marks F8 resolved; with it every D-069 finding is resolved.

### D-085 — A bound event's failure routes to the bind site (review R1)

**Decided (Dev, 2026-10-05; review R1, Claude G-2).** _The fact, verified at `f608fa7`._ `$event` captures `getOwner()` and `useContext(BOUNDARY)` when it is created (`runtime.ts:1397-1404`). _Amends_ D-072's "a failure nobody handles goes to the nearest `Errored` above the handler's creation site".

### D-086 — An unyielded block call is refused by the types and by lint (review R2)

**Decided (Dev, 2026-10-05; review R2, both reviewers).** The JSX `Fragment`'s children are typed `Element`, regenerated through `scripts/jsx-web-shared.mjs`. ### D-087 — Typed failures are branded at runtime; an attempt over a call handles only them (review R4)

**Decided (Dev, 2026-10-05; review R4, Claude G-3).** Every build marks a typed failure at run time with one non-enumerable symbol. `raise` sets it, and so does an attempt's `handle` on an `Error` its handler returns. Today `known()` / `KNOWN` mark failures in development only. An `attempt` over an event call passes only branded failures to its handler. Anything else is re-thrown past the handler: a crash is a bug, not a failure (D-019). `Caught<T>` (the call's `FailsOf`) is then exact. ### D-095 — The library's `render` / `hydrate` are the root edge, not a foreign hand-off

**Decided (Dev, 2026-10-06).** The library's own `render` and `hydrate` stay. They are not a foreign hand-off: they are the root edge, governed by D-033 (a settled root that may fail; a failure with no `Errored` is re-thrown). `foreign()` (D-088) applies only to plain-Solid code that takes a component: the router, Solid's `lazy`, `@solidjs/web`'s `render` / `hydrate` / `renderTo…`. The lint `no-unchecked-foreign-handoff` does not report the library's `render` / `hydrate`, and keeps reporting `@solidjs/web`'s when handed a block component. Dev considered replacing the wrappers with Solid's `render` and a `root()` checker, and decided against it ("bring back the library's own render and hydrate — and exempt them").
_Alternatives:_ delete the wrappers for `@solidjs/web`'s `render` plus a type-only `root(App)` (settled, may fail) next to `foreign(App)` (may pend, never fails). Rejected for now. Or apply `foreign()` at the root, as D-088's first implementation did. That was wrong: it forbade a failing root, against D-033, and would allow a pending one, which Solid cannot show.
_Reasoning:_ the root is where D-033 puts an unhandled failure. A checker that refuses failures there says the opposite of D-033. A pending root has nowhere to show, which is why the library's `render` refuses one.
_Clarifies_ D-088 (its "`render`" is `@solidjs/web`'s); _updates_ D-023's validation count; _fixes_ a D-004 breach (below).

_Implemented._

- **Lint.** `no-unchecked-foreign-handoff` already reported only `render` / `hydrate` / `renderTo…` imported from `@solidjs/web` or `solid-js/web`. Its comments, description and the plugin's README now say why the library's are not reported: they are the root edge. New tests: without types, the library's `hydrate(() => Live(), document)` is valid. With types, the library's `render(Failing, root)` and `hydrate(() => Failing(…), document)` are valid (a failing root), and `@solidjs/web`'s `renderToString(() => Failing(…))` is reported, naming `ApiError`.
- **rendering's entries: not done as ruled.** The ruling moves them back to `render(App)` / `hydrate(App)` through the library's `render` and removes `App`'s added `Errored`. Two facts stand against it:
  1. `App` is pending at its root by design, as the original is (CSR's `render` defers the mount, streaming SSR holds the response, string SSR's entry wraps the app in a `Loading`). Its type is `ComponentView<true, never, true>`. The library's `render` / `hydrate` refuse it: `render(App, root)`, `render(() => App(), root)` and `hydrate(() => Shell({ …, children: function* () { return <>{yield* App()}</>; } }), document)` are type errors (`Type 'true' is not assignable to type 'false'` at `[PENDING]`; checked against the twin's tsconfig).   2. Two of the four entries are server entries, through `@solidjs/web`'s `renderToString` / `renderToStream`. The library has no server renderer, and this ruling counts those renderers as foreign. So `App` reaches them through `foreign(App)`, and `foreign` refuses a failing `App`.

  Making the library's `render` take this root needs a `Loading` at the app's root, which changes what the CSR and streaming variants show while pending (a fallback, against the original's deferred mount and held response). It also needs a library server renderer. Neither is in this ruling. So the twin is unchanged: its entries hand `foreign(App)` / `foreign(Shell)` to `@solidjs/web`, and `App`'s `Errored` around the pages stays. Under this ruling it is at a real foreign edge. A test does not need the `Errored`: the twin's parity and behaviour tests mount `App` through `createComponent`, not through the entries. The server entries and `foreign` do. Open for Dev: keep it, or give the root edge a pending form (a library `render` that takes a pending root, plus library `renderToString` / `renderToStream`), after which `App`'s `Errored` could go.

- **D-023's count.** Recounted after the change: hackernews-spa 3 and room 1, which is the ruling's 4, plus rendering 1 (above), so 5. Each is at a real foreign edge (the router, or `@solidjs/web`'s renderers). No twin has a boundary for the library's `render` / `hydrate`.
- **D-004 fix (review I-3).** `solid-blocks/h` copied `@solidjs/h`'s internal element brand onto its thunks, finding it as the first own symbol of `solidH("div")` (`h.ts`). `isElementThunk` in `render.ts` and `flow.ts` recognised an element thunk by a symbol whose description is `"hyper-element"`.   - `solid-blocks/h` returns `solidH(build)`, where `build` is a component that converts the arguments and returns `solidH(…converted)`. The thunk is of Solid's own making: Solid's `h` brands it, materializes it in place where it meets one (a child, a component's output), and calls `build` afresh on each materialization (so each one converts the arguments afresh, as before). The library never reads or writes Solid's symbol.   - The library marks its own output with `ELEMENT_MARK` (`Symbol.for("solid.blocks.element")`, in the runtime). The automatic `jsx()` runtime is built on `h`, so its output carries the same mark. `render`'s and the boundaries' `isElementThunk` check only that mark.
  - **A raw `@solidjs/h` thunk is not a root.** Nothing public tells it apart from any other function, so `render` takes the library's forms only: `render(App)`, `render(() => <App />)`, `render(() => jsx(App, {}))` and `render(() => h(App, {}))`. This is now a rule in §7, pinned by nojsx.type-tests (`render(() => solidH("p", "x"))` and `render(() => solidH(Settled, {}))` are refused, `h`'s forms accepted; with the directives removed the errors are `HyperElement` not assignable to `Element | View<false, any>`). render-thunk.spec's fourth form was `@solidjs/h`'s `jsx` (cast); it is now `solid-blocks/h`'s `h(App, {})`, and all four forms keep state across a `Loading` round trip.

### D-098 — Context requirements are a fourth color

**Decided (Dev, 2026-10-06).** `yield* Ctx` in a setup (the `ContextRead` op, D-036) yields `ContextRead<typeof Ctx>`, and `component()` folds the setup's ops: `Requires<Ctx>` joins `ComponentView` beside `P`, `E` and `W`, as `FailsOf<Y>` does for D-073. (a) A context created without a default (`createContext<T>()`) is a requirement when read; one with a default (D-060's `constant`, or any value) is not. Reading a required context with no provider above is the development error `[NO_PROVIDER]`, at the read. (b) `Ctx.provide({ value, children })` is a call-form yield component (D-062, D-066; Solid's provider tag is foreign and cannot discharge a type). Its output subtracts `Requires<Ctx>` from the requirements of the components called inside its `children`, never from the enclosing component's own setup read, which was resolved where that component was created: a provider inside its own view is ineffective, exactly as in Solid, and the requirement then surfaces at the root. (c) Requires propagates like the other colors through calls, holes and rows; `render` / `hydrate` and `foreign()` demand `Requires = never` with a branded message naming the missing context. (d) Context is read in setups only (unchanged); a provided value is wrapped as a source, as props are (D-042).
_Alternatives:_ the plain-function design, explored and rejected. Components as plain functions, with lazy context handles resolved at the read. It made the requirement positional: a provider in the same component's view would wrongly discharge a read resolved above it (the memo case: a memo created in the setup reads the context under the component's owner, above any provider in its view); or memos become positional; or memo reads of context must be refused. Dev rejected all three and kept setup routines, where the requirement has one meaning (the setup's read, resolved at creation) and one channel (the component's type).
_Reasoning:_ a context read with no provider is a failure the types can see before it happens, and the setup is the one place a context is read, so the requirement is the component's, stated once. Discharge follows Solid's own resolution: a provider gives what is created under it.

_Implemented._

- **Types** (`types.ts`, `context.ts`). `REQUIRES` phantom; `ContextRead<C>` (`C` the context, or `never` for a defaulted one); `RequiresOf<Y>`; `ChildView`, `View`, `HView`, `ComponentView`, `Component` take a fourth parameter `R`, default `never` (the quiet case, as a bare prop is settled, D-024: an annotation without it requires nothing; `SettledView` and an element require nothing). `component()`'s view: `ViewRequires<VY, R> | RequiresOf<Y>`. Flow controls, boundaries, `lazy` and `h` carry their children's requirements. `createContext<T, N extends string = string>()` returns `RequiredContext<T, N>`, `createContext(defaultValue)` a `YieldContext<T, N>`; both are Solid's `Context<T>` (taggable, foreign) with `[Symbol.iterator]` and `provide`. A requirement's identity is the context's type: its value type is invariant (a phantom `(value: T) => T`), so a provider of another value type, narrower or wider, discharges nothing; the optional name `N` tells apart two contexts of one value type and is what the refusal prints. **The ruling's message ("App requires UserCtx: provide it above App") could not be had in full**: a type cannot name the component (as for D-088), nor the variable a context is bound to. The refusal names the context by its name literal when it has one (`createContext<User, "UserCtx">()`), else by its type (`RequiredContext<User, string>`): `render`'s / `hydrate`'s `RootCheck` is `{ "[NO_PROVIDER] the root requires the contexts this property names: provide each above the components that read it (Ctx.provide({ value, children }) around their calls)": "UserCtx" }`; `foreign`'s `ForeignCheck` gains the same property.
- **(d), read as props are.** `yield* Ctx` gives a path over the provided value (`ContextValue<T>`: `Path<T>`, or `Path<V, E, P>` for a context declared `Source<V, E, P>`), and `provide`'s `value` takes what a prop takes (a value, a source, a hole; `ProvidedValue<T>`). So a setup never holds a context's value: an event handler in a context is read in the event that calls it, `yield* (yield* save)(x)`, and bound `onClick={yield* (yield* save)}`, as an event prop is (D-042). A context's value is a bag of sources the same way a component's props are. The runtime wraps what Solid's `useContext` returns (a provided value, a tag's, or the default), so the provider tag still gives a value at run time.
- **`provide`'s runtime** (`flow.ts` `provideView`): Solid's provider of the context, created untracked as a flow control is, its `children` a lazy view built inside it. In `h`, `h(Ctx.provide, { value }, ...children)` (an overload reads `provide`'s phantom `[PROVIDES]`); Solid's `h` hands a function prop over as a getter, so a source or a hole given as `value` is kept a source (`getterSource`).
- **Found implementing: two places the types would have under-stated, now held.**
  1. _A hole prop._ A prop declares pending and failure, not a requirement, and a component's type is a plain function's (D-068: a generic over its arguments would break D-029's generic components), so a call's type cannot take its hole props' requirements. A hole prop is therefore `ChildView<…, never>`: a requiring component called in a user component's hole prop is refused (provide inside the hole, around the call). ### D-102 — `foreign(Comp, { provided: [Ctx, …] })`: the providers above a foreign edge

**Decided (Dev, 2026-10-06; from a first-time-user review, log item 22).** A yield component handed to plain Solid (D-088) may list the contexts provided above the foreign edge — typically an app-wide `Ctx.provide` around a router whose route renders it: `defineRoute({ component: foreign(Settings, { provided: [ThemeCtx] }) })`. The type takes those contexts off the component's requirements (D-098) before `foreign`'s `[NO_PROVIDER]` check; what remains is still refused, named. A listed context the component does not require (it does not read it, or reads it with a default) is a type error, `[NOT_REQUIRED]`, naming it, so the list stays the true one. The claim is the author's, and the runtime checks it where the component is created: with no provider above, its setup's read is `NO_PROVIDER` (development; Solid's own context error in production). `foreign` stays the identity at run time; the options are not read.
_Alternatives:_ **providers inside each route** (what the dialect required before: each route page provides the app-wide context itself) — defeats "the whole app provides it" and gives each page its own value, so an app-wide theme or identity would not be one; **a router wrapper** (a library `Router` that is a yield component and carries its routes' requirements through its type) — the routes are values in a table the router reads at run time, so the wrapper would need its own route DSL typed per route, and it ties the library to one router's API (D-004 keeps the library on Solid's public API); **an unchecked cast** (`foreign(Page as unknown as () => unknown) as never`, the reviewer's workaround) — it also discards the failure check.
_Reasoning:_ the edge is where the type loses the tree: plain Solid renders the route with no `yield*`, so nothing can carry the requirement from the route to the provider above the router. The author knows what is above the router, and the runtime already checks what the author says at the one place it can be wrong (the route's creation), so stating it costs one list and keeps the check. Refusing an unneeded entry keeps the list from drifting into a blanket "everything is provided".

_Implemented._

- **Types** (`foreign.ts`). `foreign<C, const P extends readonly AnyContext[] = []>(component: C & ForeignCheck<C, P[number]>, options?: ForeignOptions<P & ProvidedCheck<C, P[number]>>)`. `ForeignCheck` takes the provided contexts (`Exclude<Settle<R>, Provided>`); its `[NO_PROVIDER]` message now ends "or list the ones provided above the foreign edge: foreign(Comp, { provided: [Ctx] })". `ProvidedCheck` is `[NOT_REQUIRED] foreign's provided lists contexts the component does not require (this property names them): remove them`, the property's type the names. Exported: `ForeignOptions`, `ProvidedCheck`. The lint (`no-unchecked-foreign-handoff`) already accepts any `foreign(…)` call.
- **Runtime.** Unchanged: `readContext` already throws `NO_PROVIDER` at the route component's setup when no provider is above (confirmed by the new test).
- **Tests.** `context.type-tests.tsx` "D-102": the identity; both of two requirements listed, either order; one of two listed (the other still `[NO_PROVIDER]`, named); a context the component does not require, an extra one beside a required one, a defaulted one (`[NOT_REQUIRED]`); `provided: []`; a failing component with its context listed is still `[FOREIGN_HANDOFF]`; both messages as printed. `foreign-provided.spec.tsx`: a plain-Solid router renders `foreign(Settings, { provided: [ThemeCtx] })` under a `ThemeCtx.provide` in a yield App and the page reads the value; with no provider above, mounting is `NO_PROVIDER` at the page's creation (development and production builds).
- **Twins.** **room-yield**: `IdentityContext` is required again (`createContext<Source<Identity | null>, "IdentityCtx">()`), as the original's is (it throws outside its provider), and `routes.ts` hands `foreign(Live, { provided: [IdentityCtx] })` to the router. Its `null` remains the provided value's (the server's identity and the client's until it mints one), so the four readers' null-checks stay: they were for "not minted yet", never only for "no provider" (D-098's row). Without `provided`, room's typecheck is `[NO_PROVIDER] … "IdentityCtx"`. **hackernews-spa-yield**: unchanged — it has no context (nor does its original), so its three `foreign(…)` routes require nothing.
- **Docs.** getting-started's app-shell recipe (a router under an app-wide context), refusals.md (`[NO_PROVIDER]`'s row, `[NOT_REQUIRED]`), yield-library.md §1. Changeset `foreign-provided.md`.
