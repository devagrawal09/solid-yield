# Generator blocks as a library: `solid-blocks`

Status: implemented. Built on the Solid fork's `blocks-lib` branch (cut from `upstream/next` at 644eaf3b) and extracted to this repository at `6978eb83` (Phase 3, D-015); it runs on published Solid (`^2.0.0-rc.11`, resolving to rc.13). Eight example twins run on it. This document is the reference for what the library is, what it enforces and where, what it costs, and what it cannot do without a blocks compiler.

## 1. What it is

Generator blocks — `$component(function* (props) { setup; return view(function* () { view }) })` — as a userland library on stock Solid 2. Nothing in `@solidjs/signals`, `solid-js` or `@solidjs/web` changes. Two pieces sit outside the runtime package. There is no build tool: prop colors are declared (§6), so nothing infers them across modules.

| Package                                      | What                                                                                                                                                         | Kind                       |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------- |
| `solid-blocks`                            | runtime interpreter, strict types, flow controls, render / hydrate, a settled-only JSX namespace, the no-JSX `h` wrapper, an automatic JSX runtime | userland (public API only) |
| `vite-plugin-solid-blocks`                | **one syntactic rule**, run before Solid's JSX compiler (`yield*` inside JSX → `perform(…)`), as a Vite plugin, a Babel plugin and a `transform()`; also the library `lazy`'s module URL (D-003, D-043, D-047) | transform |
| `eslint-plugin-solid-blocks`              | fourteen rules for what TypeScript cannot express | lint |

### Surface

**JSX is for DOM elements and foreign components; a block component is called; its props are sources, holes or values; its children are a generator** (D-062, D-065, D-066, D-067). A `$component`, a `lazy` component, or a flow control or boundary is written `{yield* Card({ todo, children: function* () { return <…/>; } })}`. Its pending and failures reach the holding view through the `yield*`, which a tag cannot carry: a tag's type is always `JSX.Element`. A tag naming a block component is a type error (the JSX namespace's `ElementType` is `TagType`: a string, or a function without the component brand) and the lint error `no-component-tag` (autofix). A call not delegated to (`<>{Card({ todo })}</>`, `{[Main(), Footer()]}`) renders, but its colors reach no type: a pending or failing one is a type error in an element or a fragment (`Fragment`'s children are `Element`, D-086; TypeScript checks a fragment only when the tsconfig sets `jsxFactory` and `jsxFragmentFactory`), and any one is the lint error `component-call-yielded` (autofix). A prop is a source (`todo`), a zero-arity `function*` hole the child reads with `yield*` as it reads a source (`total: function* () { return (yield* n) * 2; }`, run in the child's reading computation), or a settled value. Each is checked at the call against the prop's declared color (§6). A `yield*` in the argument object would read in the caller's hole and re-create the child on every change, so it is the lint error `no-read-in-prop`. `children` is always a generator: `function* () { return <…/>; }` is a lazy view, built where and when the child shows it; a list's or a branch's children are a row, `function* (item, index) { … }`. A plain-JSX `children` is the lint error `component-children-generator`. A flow control's `fallback` may be a lazy view too, `Errored`'s included, so a component in it is set up only when the fallback shows. Foreign components stay tags: the router's `Router`, Solid's `Reveal` and `Portal`, `HydrationScript`, and a context's provider.

- **Components and blocks**: `$component`, `lazy` (Solid's `lazy()` with the same signature, as a block component: pending while its chunk loads, colored as the loaded component, usable in call form `{yield* Page()}`; D-047 — `adopt` is removed, and a foreign non-lazy component has no bridge), `foreign(Comp)` (D-088: a block component handed to plain Solid as a value — the router's `component`, `@solidjs/web`'s `render` — may pend but handles its own failures; the identity at run time, `[FOREIGN_HANDOFF]` in the types otherwise). A row (a render callback of `For`, `Repeat`, `Show`, `Match`, an `Errored` fallback) and a no-JSX hole are bare `function*`s; there is no wrapper (`$` and `$scope` are removed, D-013).
- **`view(fn)`** (D-054, required by D-089): `return view(function* () { return <…/>; })` is the one spelling of a view — a setup's or a row's — and type-checks it where it is written — a creation or a write in a view (or an `h` view's read) is reported at the `view(` call, naming the op, not at the `$component(` call with the whole setup's yield union; identity at run time, colors kept. TypeScript reports it at the wrapper, not at the offending `yield*` (it does not check a `yield*` against a contextual yield type). There is no `setup()` wrapper. A bare `function*` returned from a setup is a type error, `[VIEW_WRAPPER] wrap the view: return view(function* () { ... })` (`view` brands what it returns, `ViewFn<Y, R>`; a row's bare view is refused as no overload of the flow control matching), and the lint error `require-view-wrapper` (autofix) reports it; every twin view is wrapped.
- **Rows and components are one shape** (D-030): a row's body is a setup, as a `$component`'s is. It runs once per row (per item, per shown branch), untracked, with the render arguments as reads; it creates (a `yield* $memo` there is the row's, created once per item and disposed with the row) and returns the row's view generator, which only reads. A row that returns its markup directly is a dev error (`ROW_VIEW`), as a setup that returns no view is (`COMPONENT_VIEW`). A derivation several holes read is a `yield* $memo` in the setup or the row's setup; a JSX hole is a `yield*` in JSX; a no-JSX hole is a source, a path or a bare zero-arity `function*` given to `h` or to a flow control's source prop (`Show({ when: function* () { … } })`).
- **Setup operations** (`yield*` in a setup): `$signal`, `$store`, `$memo` (with `loadingValue`: not pending), `$optimistic` (the scalar form, as `$signal`), `$optimisticStore` (the object-or-body form, as `$store`: a value, or a derived body; D-014), `$projection` (a derived store; `seedLoadingValue`: not pending), `$effect(compute, effect)` (D-079: Solid's `createEffect`, both halves generators — the compute tracks and is pure, reads, `raise`s, a sync `attempt`, and returns a value; the effect phase, `function* (value, prev)`, runs after it: writes, `$cleanup`, a sync `attempt` or event call, and plain reads of settled sources, untracked because the phase is (D-083; a source that may be pending is a type error there: the phase does not wait)), `$settled` (runs once after settle, D-053), `$cleanup`,  `yield* Ctx` on a context made with the library's `createContext` — the one way to read a context (D-036: `context(Ctx)` for a foreign context is removed; a foreign context is wrapped once in a library context). A generator helper that creates (`function* createTodos() { … }`) is delegated to with `yield*`, so its creations are the setup's.
- **Constants**: `constant(value)` is a `Source<T, false, never>` that always reads `value` — usable anywhere, module level included (it needs no owner). A context whose provided values are sources defaults to one: `createContext(constant<Identity | null>(null))`; `createContext` itself stays plain (D-060).
- **Reads** (`yield*` anywhere that reads — never in a setup): sources, prop and store paths, `readStore(store, select)`, `latestOf`, `isPendingOf`. Every prop is a source; nothing gives a setup a value. **Reads track where the host tracks** (D-083): memos, holes and the compute phase subscribe; events and the effect phase do not. Tracking is a property of the host, not of the read, so there is no untrack op (`$untrack` is removed): "take the value once and ignore its updates" is a plain read in an `$event` or an `$effect`'s effect phase, untracked because Solid runs them untracked; the library adds no untrack of its own.
- **Strict**: every read and every write is a `yield*`. Typed failures are complete for library-mediated failures (`raise`, an `attempt`'s handler); a plain `throw` in a block is a bug, surfaced in development as `[UNTYPED_THROW] <host> in <Component>: …` (naming the setup / view / hole / memo / effect / event); like any failure it goes to the nearest `Errored` if there is one, otherwise it is re-thrown (D-019, D-033 — the library installs no root boundary). A view has no body (D-032): it is `function* () { return <…/>; }`, every read is a hole (a `yield*` in a JSX position; in `h` a source or a bare `function*` hole), and structure comes from flow controls (`Show(…)`, `Match(…)`, `For(…)`, …), which take sources directly — no `yield*` outside JSX, no `if` / early `return`, no local computation. A read at a JSX view's top level is the dev error `READ_IN_VIEW` and a lint error (`no-read-in-view-body`); an `h` view's type refuses any yield (`[HVIEW_READ]`, its only check, D-049 — the runtime cannot tell the flavors apart, so `READ_IN_VIEW` also fires for an `h` view reached through a cast). Flow controls take a source or a bare `function*` hole for `when` / `each` / `count` (D-038), as every block component prop now does (D-065). A setter call returns a receipt and writes only when it is delegated to (`yield* setX(v)`), so every write is a `Write` in the block's type and only an `$event` or an `$effect` accepts it; a setter call that is not delegated is a lint error (`no-unyielded-write`) and, in development, `UNYIELDED_WRITE` when its run ends (D-021: every run checks the receipts it minted; an `$event` call checks once its body ends, so a receipt minted before an async `attempt` and delegated to after it is fine); a setter called with no block running — handed to plain code, `onClick={setX}`, a timer — throws `SETTER_OUTSIDE_RUN` at the call (D-028; production keeps the silent no-op). Block code holds no reactive state the library did not create: plain Solid's primitives, the router's reactive hooks and `dynamic` are lint errors (`no-foreign-reactive`), each with its block form. There is no wrapper for foreign accessors or stores (`read`, `paths`) and no way back to a plain accessor (`accessor`).
- **Effects of failure and waiting**: `attempt(fn, onError)`: `onError` (required) turns what `fn` threw, or its promise rejected with, into the error object the block fails with, so every failure has a type, each error class its own color; when `fn` returns a promise a `$memo` / `$event` suspends on it. The handler's return decides (D-076, D-078): the failure, an `Error` with a literal `kind` (what was caught, or a transformation of it), which the attempt fails with — the only way a failure leaves the handler; nothing, which absorbs it (the attempt gives `undefined`, its value `T | undefined`); or a value `V`, which absorbs it too (the attempt gives `V`, its value `T | V`: `attempt(() => parse(s), () => null)`). Absorbed, it adds no failure to the block's type (D-073). A handler that returns an `Error` on one path and not on another is `[ATTEMPT_ABSORBS]`. **The handler may be a generator** (D-078), `function* (e) { … }`, decided by what it returns: it runs as the host's own block code — not a new host, no boundary — so its ops are the host's (an `$event`'s writes, inside its transaction, and waits; a `$memo`'s reads, `raise` and nested attempts; an `$effect`'s synchronous ones only) and its colors join the host's; `yield* raise(e)` in it fails the attempt with `e`. A retry is a nested attempt: `attempt(load, function* () { return yield* attempt(load, cause => new LoadError(cause)); })`. It runs synchronously for a synchronous throw, on rejection for a promise (inside the event's transaction, or as the memo's resumption), and per failure for a stream — after the host's run, so a stream attempt's handler is a **plain** function (D-091): it returns an `Error` (the stream fails) or nothing (the stream ends); a generator handler, or a value, is `[STREAM_HANDLER]` (and `STREAM_HANDLER` at run time). `until`'s handler follows the same rule. **An `$event` does not attempt a stream** (D-091): a stream attempt yields a `StreamAttempt`, which is not an `EventOp` (`[STREAM_IN_EVENT]`; `STREAM_IN_EVENT` in development) — events do one thing and finish, a `$memo` or a `$projection` holds what keeps arriving. `fn` may also return an event call (D-077): `yield* attempt(() => post(msg), e => { … })` is `yield* post(msg)` with the call's failure handled — the handler receives the call's typed failure (its `FailsOf`) and returns it, a transformation, or nothing — and the call's other colors are the block's as with `yield*`. Only a typed failure reaches it, in every build (D-087): `raise` and a handler's returned `Error` brand the failure at run time (one non-enumerable symbol), and anything else the call rejects with — a plain `throw`, a `TypeError` — is a crash (D-019), not a failure, and goes past the handler (`UNTYPED_THROW` in development, itself in production), so the handler's parameter type is exact. **`try` / `catch` is not a block form** (D-077): the types cannot see a `catch`, so a failure it handles would stay in the block's type; the lint error `no-try-catch` points to `attempt` or `Errored`. `raise(error)` fails with a typed error. `until(source, onError, options)` waits for a source to read truthy. `attempt` is the one place a failure gets its type: a `$memo`, `$optimisticStore` or `$projection` body that returns a promise or a stream returns it through `attempt` (`return yield* attempt(() => watch(feed), cause => new FeedError(cause))`; returning one raw is a type error). A promise is waited for; a stream (or a promise of one) is given back as itself, its failures going through the handler as they come, by a Proxy that changes only how it fails (a server function's brand, a live source's `onstatus` stay its own). `$dynamic`'s component is a plain one: its failures are not in its type.
- **Events**: `$event(function* (e) {…})` is a Solid `action`: every call is one transaction (writes are held until it settles; an async `attempt` re-enters it; a rejection is thrown at the `yield*`). It takes any arguments and returns a promise of its result, so block code does not need `action`; `yield* refresh(store)` and `yield* until(source)` are its forms of Solid's `refresh` / `until`. A failure goes to whoever handles the returned promise; one nobody handles (a DOM dispatch) goes to the nearest `Errored` above where the handler is bound (D-085). Calls are independent runs, full stop (D-064: no `latest` option); a search box that wants latest-wins reads its input through a `$memo`, whose superseded runs' results are discarded (D-080). An event has two colors in its type, apart from its failures: `P`, it reads a pending source (and waits for its data), and `A`, it does async work of its own (an async `attempt`, `until`). Calling an event is an operation: `yield* save(x)` waits for the call and joins both its colors and its failures to the caller's type (so they travel through any depth of calls). An `$effect` cannot wait, so it may delegate only to an event with neither color. **Binding** an event is the other operation (D-072): in a view's event attribute, `onClick={yield* save}` is a `Bind` op. The handler is attached un-called — through a wrapper, one per bind, that records the bind site's owner and whether an `Errored` is above it — and its failures join the view's type: the DOM calls it, nobody handles that call, and its failure goes to the nearest `Errored` above the bind site, the view whose type has it (D-085); with none there, the call's promise rejects. A handler created in one component and bound in another (passed through props or context) routes to where it is bound. A call from block code (`yield* save()`, an `attempt` over it) fails at its caller, wherever the handler is bound. Its `P` does not make the view pending — the runtime never suspends a view for a call — but marks it *may wait* (`View<P, E, W>`'s `W`, D-075), which no boundary handles and the lint warning `no-unshown-wait` reports where the handler is bound. `yield* save` binds; `yield* save(x)` calls. The bound-data form is `onClick={[yield* pick, data]}` (Solid calls `pick(data, event)`). In `h` an `$event` handler given as an attribute is the bind and carries the same colors. An event attribute of the blocks JSX namespace takes only a bound handler: `onClick={save}` (unbound), a plain function, or a value read from a source (`onClick={yield* props.onSave}`) is a type error, since the DOM would call it with its colors in no type (D-071). A handler given as a prop is called by an `$event` of the child's, which joins its colors: `yield* (yield* props.onSave)()`. The unbound form is also the lint error `no-unbound-event` (autofix: the `yield*`). `Errored`'s `reset` cannot pend or fail, so it is typed as already bound (`Reset`): `onClick={reset}`. With type information, `no-unyielded-write` reports an event call a block uses any other way. Setters return receipts (`yield* setX(v)` is a `Write`).
- **Flow and boundaries**: `For`, `Repeat`, `Show`, `Switch`, `Match`, `Loading`, `Errored` — Solid's, typed for blocks, render callbacks may be row blocks; boundaries in call form only (D-062). Failures are a union of error types, each its own color: `Errored` handles them all, or with `catch={[NotFound, …]}` only those types (its fallback receives them; any other is rethrown to the boundary above, and stays in the type). An `Errored` fallback is content, a render function `(error, reset) => …`, a lazy view, or a row `function* (error: Path<NotFound>, reset: Reset) { …; return view(…); }` (its parameters annotated: TypeScript does not infer a generator fallback's), which a view that binds an event needs. The fallback's own pending reads and failures are not the boundary's to handle: they join its output (D-071). A view with an unhandled pending read or failure is not an element: it reaches the holding view through `yield*`. At the root, `render` / `hydrate` refuse a pending view. A failing one is accepted and re-thrown when it fails, since the library installs no boundary (D-033, D-059). Every failure type is a `Failure` — an `Error` with a literal `kind` (`readonly kind = "not-found" as const`), checked at `attempt`, `until`, `raise` and `Errored`'s `catch` (D-034): TypeScript removes a handled class structurally while the runtime matches with `instanceof`, so two classes of one shape would be one type; a missing or plain-string `kind` is the type error `[FAILURE_KIND]`.
- **Mounting**: `render`, `hydrate` (a root that is not pending; it may fail, and a failure with no `Errored` is re-thrown); `solid-blocks/jsx-runtime`.
- **No-JSX**: `solid-blocks/h` — the `h` flavor (D-012 as amended by D-046: `html`` ` tagged templates are dropped).
- **Types say exactly what the runtime does** (D-071): wherever the runtime routes a color — pending, a failure — the type carries it to the same place. A color the runtime routes and the type lacks is a bug to fix, never a limitation of §7.
- **Types**: `Source<T, E, P>` (the failures second, the pending flag last, D-068), `Path<T, E, P>`, `View<P, E>`, `ComponentView<P, E>`, `Component<D, Pd, E>`, `Props<{ … }>` (the props annotation, §6), `PropsInput`, `HoleProp`, `RowBlock`, `EventHandler`, and the op types (`Read`, `Wait`, `Raise`, `Write`, `Create`, …).

### The userland route

Every operation a block delegates to with `yield*` runs inside its own iterator and returns without yielding, so `yield* count` is a plain tracked call in whatever computation is running the block. The only operation that yields to a driver is an async `attempt`: the `$memo` / `$event` runner suspends the generator on the promise and resumes it (a memo's compute returns the resumption's promise, so Solid's own async handling applies). A view generator, after the transform's rule, has no `yield` left and runs once; each hole is its own computation. Which block is running (its host, an effect's cleanups, a memo resumed after its attempt, a view's top level, a JSX-position read) is one value the runtime replaces whole for each run (`runAs`) and restores after, so a run started inside another — a view built while a memo resumes, a child's setup in a parent's view — starts from its own state (runtime "host state is per run (re-entrancy)").

What the runtime uses from Solid, all public exports: `action`, `createMemo`, `createRenderEffect`, `createSignal`, `createStore`, `createTrackedEffect`, `getObserver`, `getOwner`, `isPending`, `latest`, `onCleanup`, `onSettled`, `runWithOwner`, `untrack`, `useContext`, `createContext`, the flow controls, and `@solidjs/web`'s `render` / `hydrate` (plus `@solidjs/h` for the no-JSX flavor). The one lower-level hook is **`getObserver()`**: the runtime tells a view's own top-level read (no observer: `READ_IN_VIEW`) from a hole's (the hole's computation), and a setup's read from the first pass of a plain Solid computation the setup created. Since whole-view reads are gone (D-032) both uses are development checks (`READ_IN_VIEW`, `READ_IN_SETUP`): production never calls it. No private API, no patched core.

Two detections the userland route needs where a compiler would know statically:

- **A view that reads at its top level** is a development error when the read happens (`READ_IN_VIEW`, naming the component or row; on the server too). There is no whole-view re-render: a view runs once, and production builds do not check. Reads through `perform` — JSX positions — are never attributed to the view or setup on the stack, even when plain Solid code performs them untracked right then (a `<Reveal>` reading its `order` getter while a nested card's view is built). TypeScript cannot hold a JSX view to this: it types a `yield*` in JSX (a hole, after the transform) and one in a statement alike, and the former is how a JSX view's coloring is its holes'; a no-JSX view yields nothing, so there the type does (`[HVIEW_READ]`).
- **Row blocks** are recognized at runtime: a render callback that is a generator function runs its setup and view per row; a function marked as a view (a lazy page's output) is content, not a callback.

## 2. Two flavors

The flavors share everything above the DOM. A block component is called in both, with the same props (sources, holes or values) and the same flow controls, and its colors travel the same way. The JSX flavor writes `{yield* Card({ todo })}` and the no-JSX flavor `h(Card, { todo })`. What differs is how DOM elements are written:

|                         | JSX flavor                                                                           | No-JSX flavor                                                                                                                                                   |
| ----------------------- | ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| DOM elements            | `return <p>{yield* user.name}</p>`; each `yield*` in JSX becomes `perform(…)`, one computation per hole (the transform, its one rule) | `return h("p", null, user.name)`: a source, a path or a bare zero-arity `function*` is a hole; plain thunks are type errors (no build step) |
| Types                   | `jsxImportSource: "solid-blocks"`: only settled views are elements, only DOM elements and foreign components are tags | `h` is typed per tag and attribute; the output (`HView<P, E>`) carries its holes' colors; a no-JSX view may yield only child views (`[HVIEW_READ]`) |
| Twins                   | 6                                                                                    | 2 (`todos-blocks-h`, `sierpinski-blocks-h`)                                                                                                                     |

## 3. The rules, where each is enforced, and its test

"Types" are `@ts-expect-error` lines in `packages/blocks/test/jsx.type-tests.tsx` (JSX) and `nojsx.type-tests.ts`; "runtime" tests are in `packages/blocks/test/runtime.spec.tsx` (dev errors are development builds only; the suite also runs against production builds with them skipped); "lint" tests are `packages/eslint-plugin-blocks/test/rules.test.js`.

Separately from the rules, `packages/blocks/test/conformance` (D-039) pins the library's semantics against handwritten Solid. It runs 12 scenarios, each written in plain Solid (the oracle) and in the library dialect, through the same steps on the client, on the server and in hydration, and compares their traces event by event. Every difference is declared exactly and recorded as a finding (D-069). The library route's server output is also compared with the blocks compiler's, frozen from the fork: the markup is the same, but the hydration keys are not interchangeable (D-069 F6). That difference is pinned as a property of the two routes, not a bug: a server and its client are built with one route (D-074, §7).

**A superseded `$memo` run runs to completion; its result is discarded; put no side effects after an await** (D-080). When a memo's read changes while a run waits on an async `attempt`, a new run starts. The old one is not closed: it continues after its attempt, exactly like Solid's async memo (and the compiler route), and Solid keeps only the latest run's result, so the old run's value or failure never lands and it subscribes nothing (its reads after the attempt are untracked anyway, `READ_AFTER_ATTEMPT`). Anything it does after the await still happens: keep a memo's body free of side effects there. Tests: runtime "a memo that waits is pending; a superseded run runs to completion and its result is discarded (D-080)" and "a superseded run that fails after its attempt is discarded too"; conformance async-flights (equal to the oracle).

**An `$event` call is one transaction: what it writes before it waits is held until the call settles; to show something during the wait, write an `$optimistic`** (D-081, D-020). This is the model, not a divergence (D-069 F4). A write before an async `attempt`, an `until` or a pending read does not show while the call waits; when the call settles, the last write shows. Handwritten Solid that writes a plain signal outside an action shows it at once. An `$optimistic` (or `$optimisticStore`) write shows at once and reverts when the call settles:

```tsx
const [saving, setSaving] = yield* $signal(false);
const save = $event(function* () {
  yield* setSaving(true); // held: the view keeps `false` while the call waits
  yield* attempt(() => api.save(), cause => new SaveError(cause));
  yield* setSaving(false);
});

const [saving, setSaving] = yield* $optimistic(false);
const save = $event(function* () {
  yield* setSaving(true); // shows at once; back to `false` when the call settles
  yield* attempt(() => api.save(), cause => new SaveError(cause));
});
```

Tests: runtime "$event is an action: its writes are one transaction across an async attempt" (held) and "$optimistic / $optimisticStore: an $event's writes show at once and revert when it settles"; conformance async-event (declared F4: the DOM keeps `idle` while the call waits).

**On the server a view's holes are read before its children; the markup is unaffected** (D-084, D-069 F8). A hole is a computation the view owns: the interpreter resolves them, then descends. Handwritten Solid reads in markup order; the reads, values and markup are the same, and the client and hydrate traces are equal. Pinned: conformance blocks-row-recursive (declared F8, server).

**An `$effect` whose compute reads a pending source waits silently: no `Loading` shows it** (D-090). Only render effects (holes) notify a boundary, as in Solid; `Create<"effect">` carries no pending, so the component's view stays settled. Tests: runtime "an $effect whose compute reads a pending source waits; no Loading shows (D-090)"; raise type-tests "D-090".

## 5. The JSX transform's rule

One syntactic rule, in `vite-plugin-solid-blocks` (D-003; `vite-plugin-solid-blocks` at extraction, D-011). It runs before Solid's JSX compiler, whose packages carry nothing of blocks since D-043.

**The rule.** Inside a JSX expression container or attribute value, `yield* e` becomes `perform(e)`, imported from `blocksModule` (default `solid-blocks`). Each read becomes its own hole: the JSX compiler sees a call and treats it as dynamic, and the view generator, with no `yield` left, runs once.

- The rule is purely syntactic. It applies to the JSX of DOM elements and of foreign Solid components (D-067).
- A block-component call written as a hole, `{yield* Card({ todo })}` (D-062), is one hole: `perform(Card({ todo }))`, with its argument left as written. A read inside that argument is a lint error, `no-read-in-prop` (D-065).
- A `yield*` inside a function nested in the JSX belongs to that function, not to this JSX. A row or lazy view's own JSX has its own holes.
- The rule does not know hosts. A hole performed while a setup is the host is the runtime's `[JSX_IN_SETUP]` (D-041).

**Refused**, as a compile error with a code:

| Position | Code |
| --- | --- |
| `ref` | `BLOCKS_YIELD_IN_REF` |
| a spread attribute | `BLOCKS_YIELD_IN_SPREAD` |
| a spread child | `BLOCKS_YIELD_IN_SPREAD_CHILD` |
| a plain `yield` | `BLOCKS_PLAIN_YIELD_IN_JSX` |

The message lists every refusal as `[CODE] message (line:column)`.

An event prop is a hole since D-072: `onClick={yield* save}` becomes `onClick={perform(save)}`, which the JSX compiler evaluates once, as the element is created, and drops on the server. `perform` returns an `$event` handler as it is, so the handler is bound. That the value is a block event handler is the types' check, not the transform's (`BLOCKS_YIELD_IN_EVENT` is removed).

**Where it runs.**

- `blocks()` is the Vite plugin: `plugins: [blocks(), solid()]`, with `enforce: "pre"`. It skips a module whose source has no `function*` without parsing it.
- `babelPluginBlocks` is the same rule for a Babel pipeline.
- `transform(code, { filename })` is the rule on text. It edits only the rewritten spans, so TypeScript and formatting are kept and the source map is exact. It returns `null` when nothing changes, so a module with no hole comes back byte-identical.
- The `perform` import goes just before the module's first statement, on that statement's line, so no line moves (D-031 note).
- Every JSX twin's Vite and Vitest configs run `blocks()` before `solid()`, and so do `packages/blocks`' own test configs and the runtime-cost harness. The `h` twins have no JSX, and the plugin leaves each of their files alone (tested).

**The oracle.** Until D-043 the rule also lived in the fork's native compiler (`blocks_rule.rs`) and `@solidjs/babel-plugin`. The plugin was lifted from the Babel copy and checked against the Rust rule: compiling the plugin's output reproduced the Rust rule's compiled output byte for byte. That held for the rule's 15 cases (5 refusal codes) and one file per JSX twin, in `dom` and `ssr` modes, and for every JSX file of the six JSX twins, with nothing normalized. Refusals matched the compiler's message, position included.

Those outputs are checked in under `packages/vite-plugin-blocks/test/fixtures/` and are the oracle now. They were regenerated once, when the import moved onto the first statement's line. The ESLint rule `yield-in-jsx-hole` reports the same list and is tested against the same `rule.json`.

**`lazy` module URLs (D-047).** `@solidjs/vite-plugin` writes the `__SOLID_LAZY_MODULE__` placeholder only for `solid-js`'s `lazy`. The plugin writes the same third argument for `lazy(() => import("…"))` from the blocks module, and `solid()` resolves it. So a code-split block component carries its `moduleUrl` (rendering-blocks' pages, tested on the client and the server).

## 6. Declared colors

A **color** is what reading a value may do besides returning it: be **pending** (wait for async data) or **fail** with a typed error. Every source carries both in its type, `Source<T, E = never, P extends boolean = false>`. `E` is the failures, a union of `Failure`s (D-034), and `P` says whether the read may be pending. The order is a `Result<T, E>`'s with the flag last (D-068).

A component declares, per prop, the colors it accepts, and TypeScript checks every call site locally with ordinary generics (D-023, D-056 as amended by D-068). There is no build step, no generated file and no inference across modules.

**Declaring.** `Props<{ … }>` is the props annotation: `$component(function* TodoItem(props: Props<{ todo: Todo; label: string }>) { … })`. It maps each field to a read: `yield* props.todo`, `yield* props.todo.title` (a path), `yield* props.children` (a source). TypeScript gives a body exactly the parameter type written, so the mapping must be visible in the annotation: `$component` cannot remap a plain object type (D-068).

| Declared | Meaning | Reads in the child |
| --- | --- | --- |
| bare `T` | settled, never fails: the default (D-024) | `Read<false, never>` |
| `Source<T, E>` | sync, may fail (a validating memo; a `loadingValue` memo over an `attempt`) | `Read<false, E>` |
| `Source<T, E, true>` | may be pending and may fail: the common async case | `Read<true, E>` |
| `Source<T, never, true>` | pending, never fails | `Read<true, never>` |

There is no `Async` alias: one type names every color (D-005). `latestOf` / `isPendingOf` take a declared prop like any source. A declared failure must be a `Failure` with a literal `kind` (D-034): `Props<{ todo: Source<Todo, unknown, true> }>` is `[FAILURE_KIND]` at the declaration.

**Call sites.** A prop is passed a value, a source or path, or a zero-arity `function*` hole (D-065), and each is checked against the declared color. Variance: settled ⊂ pending, `never` ⊂ `E`.

- A bare prop takes `T`, a settled source or path, or a hole that reads only settled sources. It refuses a pending or failing source, and a hole that reads one or raises.
- A prop declared `Source<T, E, true>` takes `T`, or any source or hole of `T` failing with part of `E`, pending or not.
- `Source<T, E>` refuses a pending source.
- An error class of the same shape as `E` but another `kind` is another color, and is refused.
- `h(Comp, props)` is checked the same way, including `children` in the props object.

TypeScript prints the refusal's message in the expected type:

```
Type 'Source<Todo, never, true>' is not assignable to type 'Todo | Source<Todo, never, false> | HoleProp<Todo, never, false> | SettledProp<"[SETTLED_PROP] prop `todo` is settled: pass a settled value, or declare it Source<T, E, true>">'.
```

A type cannot name the component, so the message does not either; the call on that line is the component.

**Colors flow through calls.** A component's view carries the colors its holes read. A child reading a `Source<Todo, FetchError, true>` prop renders a `View<true, FetchError>`, and `{yield* TodoItem({ todo })}` moves those colors into the caller's view. There is no tag to drop them (D-062), so no boundary is added only for typing — except where a block component is handed to foreign code (D-088): plain Solid renders it with no `yield*`, so it must handle its own failures, and an `Errored` the original did not have may be needed there (the twins have 5: room's page, hackernews' three routes, rendering's pages; DECISIONS D-023).

**Pass-through components are generic (D-029).** A component that only forwards a prop declares its color with type parameters: `function* Card<E, P extends boolean>(props: Props<{ todo: Source<Todo, E, P> }>)`. Its view carries each caller's colors: `Card({ todo: settled })` is a `View<false, never>`, and `Card({ todo: fetched })` a `View<true, FetchError>`.

- `Component<…>` is a plain function type, so a generic component keeps its type parameters through `$component`. The component mark is on the view it returns (`ComponentView`), which `TagType` and `no-component-tag` recognise.
- The body is checked once for every color, so it may forward only into a prop that accepts any color, which means another generic one. Forwarding into a bare prop is an error.
- Generics therefore spread from a forwarder to the components that read what it forwards. In the twins, 3 forwarders made 4 readers generic: 7 components and 8 props (DECISIONS D-023, "Validation (1B)").
- A forwarder that shows the failure itself (its own `Errored` reads `err().message`) bounds its parameter: `E extends Failure`.
- In `h`, call a generic component directly: `h("ul", Card({ todo }))`. `h(Card, props)` reads `ReturnType<typeof Card>`, which TypeScript computes with the type parameters erased to their constraints.

**A declared color is permission, not a duty (D-040).** `Source<Todo, FetchError, true>` says "I may be given unsettled data"; it creates no obligation to handle it. Its pending reaches the nearest `Loading` and its failure the nearest `Errored`, wherever they are, as in Solid.

Only pending needs a position that admits it. A failure may reach a row, a call in a hole or the root, joining each enclosing view's failure type, and with no `Errored` it is re-thrown (D-033, D-059). `render` / `hydrate` accept a root that may fail, but not one that is pending.

**What it replaced.** Until Phase 1B a whole-program type linker inferred each prop's color from every render site. `@solidjs/blocks-linker`, fed by the compiler's `summarizeBlocks`, wrote a committed `solid-props.gen.d.ts` per twin, which `TypedProps<P, "Key">` read. It needed a build step, a key per component and a staleness check, and it was the gate's one pre-existing red. Across the 8 twins, the declared colors cover the same 25 of 102 props that the linker and explicit declarations colored before (DECISIONS D-023, "Validation (1B)").

## 7. Limitations (without the blocks compiler)

- **No islands.** Hydration is Solid's: every hydrated component runs. Island boundaries need per-handler reads / writes and a compiler to split chunks. (The per-module analysis that would feed one, `summarizeBlocks` with its `solid-blocks-summary` schema, was removed with the type linker in Phase 1B. The schema and its mapping onto the experiment branch's summarizers, the old §6, are in git history before `f00b389a`.)
- **No server components** (D-058). The blocks model has none: the idea is that a future compiler finds inert regions and turns them into server components itself. Server *data* (server functions, SSR) is supported; the twins whose point was server components (chat, hackernews, notes) were removed, and room's twin keeps only its live-server-function page.
- **No runtime tiers.** The app ships the full runtime plus the interpreter; selecting a sync-only or smaller runtime needs a whole-graph capability proof and a compiler to lower blocks.
- **Interpretation cost** (section 8): generator objects per setup / view / row, proxy paths for props and stores, one `perform` call per hole. That is 11–27% on synthetic workloads and 1–16% of the twins' parity scripts.
- **An effect cannot trigger an async event** (D-035, `start()` removed): an `$effect`'s effect phase delegates only to a synchronous event (its compute calls none: it is pure, D-079); work that must wait is modelled as an event calling an event, or as a `$memo`.
- **Failures with no boundary are re-thrown**: typed failures are complete for library-mediated failures; a plain throw is a bug surfaced in development (`UNTYPED_THROW`); either routes to the nearest `Errored` if there is one, otherwise it is re-thrown (D-033). The types require no boundary for a failure: it joins the holding view at a call, at a row (D-059) and at the root. Only pending needs a position that admits it (a `Loading`, which the root must have above any pending read). A failing view is still not a plain JSX child: it is `yield*`-ed into the holding view. A failure the runtime routes is in a type (D-071). An `$effect`'s or `$settled`'s raise joins its component's failures (D-073); an `$event` bound in a view, `onClick={yield* save}`, gives the view its failures and its pending read (D-072). At the root a computation's failure is re-thrown as Solid's error with the failure as its `cause`.
- **The library route and the compiler route are not mixed** (D-074, D-069 F6). They render the same markup but number hydration keys differently: the library route has Solid's owner ids (`0`, `1000`, `1010`, …), the compiler route a scope per view (`00`, `01000`, …). A page rendered on the server by one route cannot be hydrated by the other, so the server and the client are built with the same route. The conformance harness pins both key lists (`routes.spec.ts`) and the library client's misses on the compiler route's markup (`hydrate-self-test.spec.ts`).
- **Detections at run time**, not compile time: a JSX view's top-level read is found when it happens (`READ_IN_VIEW` in development, and a lint rule), not by its type; a row block is recognized by its function kind.
- **No plain Solid at the edges**: reactive state from plain Solid, the router or another library cannot enter block code (`no-foreign-reactive`); integrations are rewritten as block code (the twins: the todos data layer, the Effect saga driver, the notes search field). What crosses a server border keeps a stated coloring: two casts, each commented (chat's usage stream never rejects; a streamed row reads an index the store already holds).
- **Paths are proxies**: a path answers only reads (`yield*`), keys (a longer path), `toString` / `toJSON` / `Symbol.toPrimitive` (its description) and `then` (`undefined`, so it is never taken for a promise). A data key with one of those names cannot be read through a path (read the parent and take the key from the value). Listing a path's keys, asking for a descriptor, defining or deleting a key is a dev error (`PATH_OBJECT`); production shows no keys and refuses the change.
- **A generator `Errored` fallback is annotated.** TypeScript does not infer the parameters of a row given as `Errored`'s `fallback` (unlike a `For` / `Show` row), so they are written: `function* (error: Path<NotFound>, reset: Reset)`. Unannotated, no overload of `Errored` matches the call.
- **Types are per component**: a prop's colors are what it declares (§6), with no inference across modules. A forwarded color needs type parameters on every component it passes through, readers included (D-029). `h(GenericComp, props)` erases them, so a generic component is called directly in an `h` view. A type-level message cannot name the component it is about (`[SETTLED_PROP]` names the prop).

### Hydration keys (D-082, D-069 F5)

The library route's server output is the handwritten markup with longer `_hk` hydration keys. Each `{yield* …}` hole is an owner, and so is a flow control called in one, so the library numbers a node at least one owner level deeper than handwritten Solid.

- **Key length per level** (the conformance scenarios, D-069 F5). A level of nested rows adds 5 characters to the library's keys and 3 to the handwritten Solid's, so 2 more per level. blocks-row-recursive at row depths 0 / 1 / 2: `1000` / `100222000` / `10022200222000` (4 / 9 / 14 characters) where handwritten Solid has `100` / `104200` / `104204200` (3 / 6 / 9). A flat list's rows have one more character (`1000` / `1010` for `100` / `110`); a `Loading` called in a hole too (`200` for `20`, its placeholder `pl-20`, its record `20_fr`).

| --- | --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `renderToString` | each of the 4 | 801 | 801 | 0 | 2 | 2 → 2 | 3 → 3 |
| `renderToStream` | `/` | 1,735 | 1,742 | +7 (0.4%) | 13 | 4.23 → 5.23 | 6 → 8 |

- **Reading them.** The string entry renders every route as its `Loading` fallback above the app, so its two keys are the shell's and equal. - **Not measured.** The twin's streamed `/profile` does not finish (it blocks the process; killed after 30 s) and its `/stream` fails with a server `READ_IN_VIEW` in `MemoList` (D-082, found while measuring, not fixed).
