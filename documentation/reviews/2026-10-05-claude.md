# solid-blocks — independent design review

Reviewer: Claude (subagent), 2026-10-05. Tree: `/Users/devagr/solid-blocks`, `main` at `df06d89`. I made no edits to the repository. File:line citations are at `df06d89`. Another agent was working in the tree during the review: it has an uncommitted one-line change to `runtime.ts:422` (the `perform` view case on the server) and a new `ssr.spec.tsx` test. Neither changes the line numbers cited here.

I ran two type probes with the repo's own `tsc` against the built `dist/types`, from `$TMPDIR/probe`, outside the repo. They are cited as **[probe 1]** and **[probe 2]**. Anything I inferred without running it is marked *(speculative)*.

## 1. Verdict

The model holds together, and it is unusually honest about itself. Colors (pending, failures, and now the may-wait marker) are threaded through every op union. Hosts are explicit, and the decision log really does turn each finding into a ruling. Most decisions match the code: the D-079/D-083 effect split, the D-080 memo supersession, the D-076/D-078 attempt handler, D-072 binding, and the D-073 effect failures all do what they say.

The project's own meta-rule (D-071) is broken in at least four places, and two of them under-state failures, which is the dangerous direction:
- **The JSX `Fragment` takes `children: unknown`.** A pending, failing component dropped into `<>…</>` without `yield*` type-checks as a settled, never-failing view, and the todos twin relies on this.
- **An `$event`'s failure goes to the boundary above where it was created, but its type joins the view that binds it.**
- **The other two:** `attempt`'s handler parameter type, and colors lost at foreign components like the router.

Several §7 "limitations" are D-071 violations written up as documentation, which D-071 explicitly forbids. The prose docs and twin comments have drifted noticeably from the code. The gate cannot catch either problem: it has no SSR render, no doc check, no fragment type test, and no conformance scenario for error routing.

## 3. D-071 audit

The rule (`DECISIONS.md:696`): wherever the runtime routes a color, the type carries it to the same place, and a gap is reported, not documented away. Findings are ordered by danger. Under-statement means the type promises the color is handled when it is not.

### Under-statements (the type says handled or settled; the runtime disagrees)

**G-1. `Fragment` children are `unknown`: colors are dropped. [probe 1] Severity: high.**
`packages/blocks/jsx/jsx-runtime.d.ts:6` declares `export function Fragment(props: { children?: unknown }): unknown;`.

```tsx
const Pending = $component(function* (props: Props<{ u: Source<string, Boom, true> }>) {
  return view(function* () { return <p>{yield* props.u}</p>; });
});
const A = $component(function* () { return view(function* () { return <div>{Pending({ u })}</div>; }); }); // refused ✓
const B = $component(function* () { return view(function* () { return <>{Pending({ u })}</>; }); });      // accepted ✗
const C = $component(function* () { return view(function* () { return <>{[Pending({ u })]}</>; }); });    // accepted ✗
const t: View<false, never> = B();   // accepted: settled, never fails
render(B, document.body);            // accepted: a pending root
```

- `tsc` reports only `A`.
- At runtime, `B` is pending and fails with `Boom`.
- The todos twin's `TodoApp` (`app.tsx:269`) depends on this. Its `Loading` output is typed settled and never failing, while `MainSection` / `Footer` are pending and may fail with `ApiError`.
- refusals.md:25 says this case is refused by "`JSX.Element` is settled only". It is not refused inside a fragment.
- Fragments are everywhere in the call form (`return <>{yield* X()}</>`), so this hole is on the main path.

**G-2. An `$event` bound in a different component from where it was created. [probe 2] Severity: high.**

How the two sides differ:
- **Types.** A `Bind<W, E>` joins `E` to the *binding* view (`types.ts:94-107`, D-072).
- **Runtime.** `$event` captures `getOwner()` and `useContext(BOUNDARY)` *at creation* (`runtime.ts:1390-1397`). An unhandled call (a DOM dispatch) reaches `reportError(owner, …)` only if a boundary was above the *creation* site. Otherwise the promise rejects and nobody handles it (`runtime.ts:1421-1427`).

So the binding's `Errored` never sees the failure. The type checks clean (probe 2):

```tsx
const Ctx = createContext<{ save: EventHandler<[], SaveError, void, false, false> }>();
const Child = $component(function* () {
  const { save } = yield* Ctx;
  return view(function* () { return <button onClick={yield* save}>save</button>; });
});
const Parent = $component(function* () {
  const save = $event(function* () { yield* raise(new SaveError()); }); // created here, no Errored above
  return view(function* () {
    return <Ctx value={{ save }}>{yield* Errored({ fallback: "handled",
      children: function* () { return <>{yield* Child()}</>; } })}</Ctx>;
  });
});
const t: View<false, never> = Parent(); // type: handled. Runtime: unhandled rejection.
```

- The same holds for `onClick={yield* (yield* props.save)}`, a handler passed as a prop and then bound, which also type-checks.
- In `h`, every `$event` attribute is a bind, so the gap applies there too.
- With an `Errored` above *both* sites, the failure goes to the wrong one: the creation site's.
- The only runtime test for this behaviour covers the case where the handler is created and bound in the same component (`runtime.spec.tsx:2789-2814`).
- The conformance port did not include "error-routing" or "owner-routing" (`COVERAGE.md`, "Not ported"), which are exactly the scenarios that would have found this.
- The twins happen to always create and bind in the same component, so nothing in the twins exercises it.

**G-3. An `attempt` over an event call types the handler's parameter as the call's `FailsOf`, but it receives anything the call rejects with. Severity: medium.**
- `Caught<T> = T extends EventCall<any, infer E, …> ? E : unknown` (`runtime.ts:709`).
- The runtime catches every rejection of the call and passes it to `handle(onError, e)` (`runtime.ts:621-632`).
- A plain `throw` or a runtime `TypeError` inside the called event reaches a handler typed `(e: SendError) => …`. In development it arrives as an `UNTYPED_THROW` `Error`; in production as the raw error, since `known()` / `KNOWN` are development-only (`runtime.ts:117-131`).
- HANDOFF.md:125 records this but it is not ruled. Under D-071 it needs a ruling (Q4 below).

**G-4. Foreign components that render block content lose colors. Severity: medium.**
- The router (I-1) and `render` for a root that is pending by design (`blocks-library.md:235`).
- room's `route()` covers it by *requiring* `never` failures, and that requirement is what pushed the twin into an extra boundary (I-2).
- The context-provider tags are safe only because their `children` are typed `Element` (settled).

**G-5. *(speculative)* An `$effect` compute that reads a pending source.**
- `ComputeOp` admits `Read<boolean, any>` (`types.ts:180`), and `$effect` returns `Create<"effect", E>`, which has no pending bit (`runtime.ts:1212-1216`).
- If Solid 2's `createEffect` compute, throwing `NotReadyError`, holds the nearest `Loading` (I did not verify this against rc.13), the component's view type under-states pending.
- One runtime test settles it either way.

**G-6. *(speculative, low)* `createContext<T>()` with no default.**
- `yield* Ctx` is typed `T` (`runtime.ts:1292-1298`).
- With no provider, Solid returns `undefined`, or throws a context-not-found error depending on the RC. I did not check which for rc.13.
- If it throws, a setup fails with an error its type (`SetupOp` has no `Raise`) cannot carry.

### Over-statements, or ops the type admits that the runtime refuses

**G-7. A generator handler on a *stream* attempt. Severity: medium.**
- **Types.** `AttemptOps` folds the handler's yields into the host's ops, so a `$memo`'s handler may read or wait, and an `$event`'s may write "inside its transaction" (§1).
- **Runtime.** For a stream, the handler runs later, outside the host's run:
  - `runAs(host, …, resumed = true)` with `drive(r, SYNC_RUN)` (`runtime.ts:649-662`), called from `mapStream`'s rejection path (`:1084-1088`).
  - Any read throws `READ_AFTER_ATTEMPT` in development (`checkRead`, `:303-307`, because `resumed` is set).
  - Any wait throws `ASYNC_NOT_ALLOWED` in every build (`drive`, `:580-593`).
  - An event's write lands outside its transaction.

§1 describes the stream case in prose ("synchronously"). That is exactly the "documented away" form D-071 forbids.

**G-8. `EventCall<R, …> extends Promise<R | undefined>`. Severity: low.**
- `undefined` happens only when an *unhandled* call is routed to a boundary (`runtime.ts:1421-1425`).
- An `await` or `yield*` sets `handled = true` before the rejection handler runs (`:1430-1433`, `:1440`), so no awaiting caller can ever observe `undefined`. The type over-states for every caller who can read the value.

**G-9. `View`'s `W` defaults to `boolean`, so annotated views count as may-wait (HANDOFF.md:123). Severity: low.**
It is a marker, and only a warning reads it, but it is still a type saying something the runtime does not do.

### What holds (checked, no gap)

- D-073: effect and `$settled` failures join the component (`runtime.ts:1567-1580` with `:1212-1260`).
- D-059 and D-063: rows (`flow.ts:82`, `RowOps`).
- D-072's fallback colors on `Errored` (`flow.ts:405-435`).
- D-034's kind check at every entry point.
- D-080's discard.
- D-083: no untrack op; the effect phase admits only `Read<false>`.

## 4. Risks

### Technical

- **TypeScript inference limits** (the model sits on generator-yield inference). Known and recorded:
  - Errors land at `view(` or `$component(`, not at the offending `yield*` (D-054).
  - `Errored`'s generator fallback needs annotated parameters (§7).
  - `h(Generic, …)` erases type parameters (D-029).
  - A recursive `Content` makes `h(Errored, …)` "excessively deep" (D-072).

  Not measured: `tsc` time and memory on the twins. The color unions grow with every hole and every call.

  *(speculative)* Generator typing has shifted across TS versions (`strictBuiltinIteratorReturn`, the `TReturn` defaults). The devDependency is TS `^6.0.3`, and no minimum TypeScript version is stated or tested for consumers.

- **Solid RC drift.** The runtime depends on RC-shaped surfaces:
  - `createEffect(compute, { effect, error })`.
  - `action`'s generator protocol, including how a nested action merges into the outer one.
  - `NotReadyError` as the pending signal.
  - `getObserver()` timing.
  - The server `For` / `Show` reading props synchronously, which F7 and the `propRead` fix are tuned to (`flow.ts:157-167`, `runtime.ts:1517-1526`).
  - The `hyper-element` symbol (I-3).

  The parity tests are the only canary, and they run development builds only (`todos-blocks/vite.config.mjs:13-15`, `room-blocks/vitest.config.ts:45`).

- **Hydration and SSR.**
  - Keys are deeper (F5): +2 characters per level, measured at only +0.4% on shallow pages, but it grows with depth.
  - The two routes cannot be mixed (F6/D-074).
  - The streamed `/profile` hang is open (D-082).
  - The server-side `READ_IN_VIEW` detector has now produced two false positives (F7, then `/stream`). Each was patched at the point of failure. *(speculative)* There will be a third. Consider making `READ_IN_VIEW` client-only, or a warning on the server.
  - In-flight work is changing `perform`'s server behaviour for views (`runtime.ts:422`, uncommitted).

- **Performance.**
  - Measured cost: 1–16% of the twins' parity-script wall time, and 11–27% on synthetic workloads (§8).
  - Not measured: memory and GC. Every path read allocates a Proxy, and every hole and every flow control called in a hole is an extra owner (F5's cause).
  - The 1,000-row update workload (+27%) is the one that scales with app size.

- **Bundle.** +3.9–5.2 KB gz fixed cost (§9). The `h` flavor costs +59% on sierpinski. Fine for a lab; a hard sell for a public package.

### Product (DX cliffs a newcomer hits)

1. **Forgetting `yield*` on a component call inside a fragment drops its colors silently** (G-1). This is the most natural slip in the call form.
2. **Binding an event that came from context or props** type-checks, then fails unhandled at runtime (G-2).
3. **In production, `setX(v)` without `yield*` is a silent no-op** (D-028 keeps production silent). The development check (D-021) and the lint are the only guards, and the twins never run production builds in the gate.
4. **The call form is verbose.** Component `.tsx` lines in twin vs. original: todos 156 → 303, effect 424 → 681, hackernews-spa 278 → 475, sierpinski 115 → 283, rendering 690 → 1,225, room `live.tsx` 424 → 779 (about 1.6–2.5x). The nesting shape `{yield* Show({ when: function* () { … }, children: function* () { return (…); } })}` is where the extra length comes from. This is the price D-062 / D-066 accepted. It is worth stating as a measured number in §9, so the compiler route has a target to beat.
5. **Error messages are poor.**
   - Brand messages are printed inside very large union types (the §6 `[SETTLED_PROP]` example is 260 characters).
   - `[ATTEMPT_ABSORBS]` is printed for any wrong handler value (HANDOFF.md:124).
   - Errors land at the wrapper, not the line.
6. **`readStore` vs. a path read is a hidden distinction.** `select(yield* store)` and `yield* readStore(store, select)` look equivalent. In an `$event`, only the second waits on a pending store, because the selector runs inside `readOf`, where `eventRead` catches `NotReadyError` (`runtime.ts:541-565`, `:343-354`). The docs don't explain why both exist.

### Process (gate blind spots like the one just found)

- **No step renders a twin's pages on the server.** This one is known, and `/profile` is still open.
- **No step runs `vite build` for any twin**, although §9 lists "`vite build` for every variant" among each twin's checks.
- **Twin parity runs development builds only.** Production-only behaviour never meets a real app in the gate: silent setters, an `UNTYPED_THROW` arriving unwrapped, receipts not checked.
- **Lint warnings never fail.** The twins run `eslint src` without `--max-warnings`, so `no-unshown-wait` and `prefer-view-wrapper` can drift without bound.
- **No type test covers fragment children** (G-1). No conformance scenario covers error routing across components (G-2).
- **Nothing checks the prose docs.** getting-started's program is type-checked and run, which is good. But blocks-library.md, refusals.md, the READMEs and the twin comments are free text, and §2b shows the drift. Cheap fix: a gate step that greps docs, READMEs and source comments for removed identifiers (`$untrack`, `$dynamic`, `adopt`, `context(`, `start(`, `paths`, `read(`, `TypedProps`, `Async<`, `createTrackedEffect`, "row is settled").
- **A step that turns SKIP is not counted red** (`blocks-gate-baseline.md`, "What green means").
- **The baseline doc is stale.** It still describes the Phase 4 reference run and needs re-stamping after Phase 5.

## 5. Opportunities and ideas

### What the model enables that is not yet used

- **Inertness is already in the types.** A view whose op union has no `Bind`, whose setup has no `Create<"signal" | "store" | …>` and no `Write` anywhere, is statically inert. A type-level `Inert<C>` (or a lint report over the twins) would produce today the data D-058's "a future compiler finds inert regions" needs. It also gives islands candidates (§7, "No islands") without a compiler.
- **A strict root.** Typed failures make an opt-in `renderStrict(App)` possible: it would accept only `View<false, never>`, a whole-app guarantee that no typed failure escapes. Today `render` accepts any failing root (D-033). The opt-in costs nothing at runtime.
- **A sync fast path.** Events already carry `P` and `A`. An event with neither could be called synchronously without a transaction. D-020 said revisit "on a measured cliff", and the colors make the case decidable per event.
- **Component color signatures as API docs.** The colors are first-class, so each component's `ComponentView<P, E, W>` and each prop's declared color could be generated into documentation.
- **The conformance harness can compare more than keys.** It already compares the library route with the compiler route's frozen server markup. It could compare *traces* against the compiler route too, once the fork can emit them. That would make the "strict vs ergonomic" claim testable.

### What the compiler route could take from here

- **D-071 as an invariant, plus the method:** an oracle, declared differences, and nothing normalized away.
- **The op and color algebra:** `Bind` / may-wait, `Create<K, E>` for effect failures, `EventCallOp<P, A, E>`, `Failure` with a literal `kind`. The compiler can carry these through *tags*, which would let the ergonomic route bring tags back without losing colors. That is the main thing D-062 gave up.
- **Statically, for free:**
  - Bind-site failure routing (G-2), because the compiler knows the binding element's owner.
  - `READ_IN_VIEW` / `JSX_IN_SETUP` as compile errors, not development errors.
  - Hydration-id scopes per view (F6), which remove F5's cost.
- **The refusals table** as the spec of what the ergonomic route may relax.

### Simplify further (D-005 candidates, by name)

| Candidate | Why |
| --- | --- |
| `TypedStore<T>` | identical to `Path<T>` (`types.ts:319`) |
| `SettledSource<T>` | identical to `Source<T>` given the defaults (`types.ts:276`) |
| `RowPending` | identical to `ViewPending` (`types.ts:586`) |
| `view()` vs a bare view generator | Two spellings of one thing. Every twin view is already wrapped, so make `view(…)` the only form: the setup's return type requires the view brand, and `prefer-view-wrapper` goes. See Q7. |
| `Errored`'s four fallback forms (content, `(err, reset) =>`, lazy view, row) | D-066 made children generator-only; the fallback could follow. The render-function form overlaps the row form. See Q8. |
| `Content` children in JSX (I-5) | Keep content children for `h` only, or type JSX children as generators only. |
| `no-dollar-block` | A deprecation rule for an API no public user has ever had. Drop it before the first release. |
| `perform`, `isComponent`, `READ`, `VIEW_MARK`, `holeOf`, `rowArg`, `runRow`, … in the main entry (`index.ts:39-50`) | Internal, but public in practice. Move them to `solid-blocks/internal` (the transform imports `perform` from there). |
| `EffectOp` | Rename `SettledOp`: since D-079 it serves only `$settled`. |
| The three overlapping rule tables (blocks-library §3/§4, refusals.md, getting-started's table) | Generate them from one source: the dev-error codes in `runtime.ts`, `REFUSALS` in `rule.js`, and each lint rule's `meta`. That also closes the drift gap. |

### Type-level and lint-level checks to add

- **Type:** `Fragment`'s children typed as `Element`, like an intrinsic element's (fixes G-1). Plus a type test for `<>{Comp()}</>` and `<>{[Comp()]}</>`.
- **Lint `component-call-yielded`:** a block-component or flow-control call in a JSX position without `yield*` is an error. This is the lint half of G-1, and works without types for the syntactic case.
- **Lint `no-unused-block-state`:** an unused `$signal` / `$memo` / `$event` binding. It would have caught `todos-blocks/src/app.tsx:45-48`.
- **Runtime:** an always-on brand on typed failures (Q4). This makes `attempt`'s handler type exact and lets untyped throws bypass handlers in every build.
- **Type:** a stream-handler op set (Q5).
- **Gate:** `--max-warnings` on twin lint, a twin SSR-render step, a `vite build` step, and the doc-drift grep (§4).

## 6. Open design questions for Dev

### Q1. Where does a bound event's failure go?

```tsx
const Parent = $component(function* () {
  const save = $event(function* () { yield* raise(new SaveError()); });
  return view(function* () {
    return <>{yield* Errored({ fallback: "x", children: function* () { return <>{yield* Child({ save })}</>; } })}</>;
  });
});
// Child: <button onClick={yield* (yield* props.save)}>
// type: the Errored around Child handles SaveError. Runtime: the boundary above Parent's *creation*; with none, an unhandled rejection.
```

- **A. Route at the bind site.** `perform` (and `h`'s attribute bind) returns a per-bind wrapper that records the hole's owner and boundary, and an unhandled DOM call reports there. An imperative `save()` call keeps creation-site routing. The types stay as D-072 wrote them. The cost is one closure per bind.
- **B. Make the types follow the runtime.** Refuse binding a handler not created in the same component, with a lint plus a development check comparing owners. This leaves a whole class of patterns out, including context-provided handlers.
- **C. Record it in §7.** D-071 forbids this.

**Recommendation: A.** It makes "binding is a hole" literally true: a hole's failure goes to the hole's boundary. It also lets the `BOUNDARY` context and the creation-time `useContext` in `$event` go (`runtime.ts:1302-1318, 1392-1397`).

### Q2. Fragment children

```tsx
return <>{MainSection({ filter })}</>;   // pending + ApiError: accepted today, typed settled
```

- **A.** Type `Fragment`'s children as `Element` (regenerate through `jsx-web-shared.mjs`), and fix `todos-blocks/src/app.tsx:269` to `{yield* MainSection(…)}{yield* Footer(…)}`.

- **C.** Both.

**Recommendation: C.** The type is the authority. The lint gives the autofix and a better message.

### Q3. Foreign components that render block components (the router)

```ts
function route<P>(c: Component<P, boolean, never>) { return c; }   // room's own bridge
defineRoute({ path: "/", component: route(Live) });               // Live's failures must be pre-handled
```

- **A.** A library bridge, e.g. `solid-blocks/router` with a call-form `Routes` whose output view unions the route components' colors. This is the honest fix, but it means wrapping a third-party API (D-047's "build it into lazy" precedent).
- **B.** Rule that a block component handed to foreign code as a value must be `View<boolean, never>`, i.e. it may pend under the app's `Loading` but must handle its own failures. Export the checker (`foreign(Component)`) and add a lint for unchecked hand-offs. State it in §3, not §7. Then remove room's per-row `Errored`s (I-2), which are no longer needed after D-063.
- **C.** Keep the §7 text. D-071 forbids it.

**Recommendation: B now, A when a second twin needs it.** B turns the gap into a rule the type enforces.

### Q4. What does an attempt's handler receive?

```ts
yield* attempt(() => post(msg), e => { /* e: SendError — but a TypeError thrown in post's body arrives here too */ });
```

- **A.** Brand typed failures at runtime in every build: one non-enumerable symbol, set by `raise` and by `handle`'s `throw known(out)` (`runtime.ts:690, 790`). `attempt` over an event call passes a branded failure to the handler and re-throws anything else past it. `Caught<T>` is then exact. As a bonus, D-019's development-only distinction becomes available in production.
- **B.** Widen `Caught<T>` to `E | unknown` (that is, `unknown`). This loses the D-077 benefit.
- **C.** Keep it, documented (HANDOFF.md:125).

**Recommendation: A.** The cost is one property write per typed failure.

### Q5. Generator handlers on stream attempts

```ts
return yield* attempt(() => watch(feed), function* (e) { yield* setError(String(e)); return; });
// typed as the $event's ops; at runtime: outside the transaction, READ_AFTER_ATTEMPT on any read, ASYNC_NOT_ALLOWED on a wait
```

- **A.** Type it. When `Attempted<T>` is a stream, the handler's ops are `Raise | Write`-free and synchronous (a `StreamHandlerOp` union), or the handler must not be a generator.
- **B.** Make the runtime honour host semantics: re-enter the event's transaction, and allow reads before the first wait. That is complex, and an event has usually finished by the time its stream fails.
- **C.** Keep the prose.

**Recommendation: A**, with the narrower "no generator handler for a stream" as the simplest form.

### Q7. One spelling of a view

- **B.** Drop `view()` and accept errors at `$component(`.

### Q8. `Errored`'s fallback forms
