# Independent design review: `solid-blocks`

Reviewed at `main` commit `f608fa7` (`test: server-render smoke in the gate`). This was a read-only review: I did not build, install, run tests, or change the repository. The cited 35-step green result is the repository's checked-in baseline, not a result I reran (`documentation/blocks-gate-baseline.md:8-11`, `documentation/blocks-gate-baseline.md:106-120`). The decision log currently ends at D-083; there is no D-084 entry (`documentation/DECISIONS.md:847-864`).

## 1. Verdict in five sentences

The model is coherent: reads, writes, waiting, failure, setup, view, row, and event work all have one explicit place in the language. The implementation follows most decisions closely, especially D-032, D-042, D-062 through D-068, D-072 through D-083, and the conformance work records real differences instead of hiding them. It does not yet fully satisfy D-071 because `Loading` drops some runtime colors from its types, stream error handlers can type-check operations the runtime refuses, and an unyielded block call can erase colors without a type or lint error. The evidence is unusually strong for a design lab, but it is uneven: small conformance programs cover client, server, and hydration, while the real twins mostly prove client DOM parity and only now have a server-render smoke test. I would make the repository public after a documentation cleanup, but I would not publish the packages to npm until the D-071 gaps, plugin prefilter bug, hydration gap, and release metadata are settled.

## 3. D-071 audit

D-071 says any runtime-routed pending or failure color missing from the type is a bug, and that an overclaim is also wrong (`documentation/DECISIONS.md:695-697`, `documentation/DECISIONS.md:744-747`). I found three confirmed gaps and one edge that needs a focused test.

### Confirmed: `Loading({ on })` drops `on`'s failures

The call-form signature types `on` as `unknown` and computes the result only from `children` and `fallback` (`packages/blocks/src/flow.ts:354-365`). At runtime, every non-child prop, including `on`, is read through `propRead` (`packages/blocks/src/flow.ts:366-374`), and `propRead` drives a source or hole (`packages/blocks/src/flow.ts:157-167`; `packages/blocks/src/runtime.ts:1504-1511`). A failing source passed to `on` is therefore read and routed to an `Errored` above, but its failure is absent from `Loading`'s output type.

```tsx
const key = yield* $memo(function* () {
  return yield* attempt(loadKey, cause => new KeyError(cause));
});

// Runtime may raise KeyError while reading `on`.
// The current return type does not contain KeyError.
yield* Loading({ on: key, fallback: "loading", children: function* () { return <Page />; } });
```

The signature should include `Ops<O>` for an `on?: O` parameter. Whether `on`'s pending is handled by this boundary or passes above should be pinned with a runtime test; its failure certainly passes above because `Loading` is not an error boundary.

### Confirmed: `h(Loading, …)` drops fallback and `on` colors

The `h` overload accepts `fallback?: Hole` and `on?: unknown`, but its result includes only the children (`packages/blocks/src/h.ts:77-82`). The call-form `Loading` correctly includes fallback pending, failures, and may-wait (`packages/blocks/src/flow.ts:361-365`), so the two supported flavors disagree. At runtime `h` converts prop holes and hands them to the same `Loading` implementation (`packages/blocks/src/h.ts:130-166`; `packages/blocks/src/holes.ts:108-133`), so a pending or failing fallback is real.

```ts
const fallback = h(FailingFallback, {});
const page = h(Loading, { fallback, on: key }, h(Content, {}));
// Current type: colors from Content only.
// Runtime: fallback and key may also read, wait, or fail.
```

This is the same class of bug D-072 already fixed for `Errored` fallbacks (`documentation/DECISIONS.md:715`).

### Confirmed: a stream error handler may type-check a wait that runtime refuses

D-078 says a generator handler runs as the host's block code and its ops join the host (`documentation/DECISIONS.md:775-786`). `AttemptOps` always includes all generator-handler yields (`packages/blocks/src/runtime.ts:717-735`), so a handler used in an `$event` or `$memo` may include a nested async `attempt`, whose `Wait` is allowed by those host types. For a stream failure, however, the runtime handles the error later and drives the handler synchronously (`packages/blocks/src/runtime.ts:653-669`); `drive` throws `ASYNC_NOT_ALLOWED` for a wait (`packages/blocks/src/runtime.ts:586-599`). The documentation mentions the synchronous run (`packages/blocks/src/runtime.ts:771-777`) but the type does not express it.

```ts
return yield* attempt(
  () => failingStream(),
  function* () {
    // Accepted when the surrounding host admits Wait.
    return yield* attempt(() => retryOverNetwork(), cause => new RetryError(cause));
  }
);
```

The result is a type/runtime mismatch exactly in D-071's sense. Either stream handlers need a sync-only handler type, or the runtime must truly drive them asynchronously.

### Confirmed enforcement hole: an unyielded block call can erase colors

At the type level, a component call returns a colored `ComponentView` and `yield*` moves its `ChildView` colors into the caller (`packages/blocks/src/types.ts:424-465`). At runtime, calling `$component` immediately runs setup and renders the view, returning Solid content under that type fiction (`packages/blocks/src/runtime.ts:1535-1603`). If the call appears in a shape TypeScript accepts as JSX content without delegation, the runtime still executes the child but the parent generator's yield union never sees it. The todos array is a live example (`examples/todos-blocks/src/app.tsx:265-272`), and both current typecheck and lint accept it (`documentation/blocks-gate-baseline.md:106-108`).

That particular occurrence sits under `Loading`, so its pending runtime is handled and no color escapes the boundary. The general form is unsafe: move the same array outside `Loading`, or put a failing child under the wrong boundary, and the parent type can stay settled while the runtime suspends or routes a failure. A type-aware lint rule should require every block-returning call in a JSX expression, array, conditional, or fragment to be the operand of `yield*`, except at explicit foreign/root handoff sites.

### Needs a pin: `$settled` accepts a pending read but does not wait

`EffectOp`, used by `$settled`, admits `Read<boolean, E>` (`packages/blocks/src/types.ts:165-174`), while `$settled` only carries its failures into the component (`packages/blocks/src/runtime.ts:1254-1270`). Only an event turns `NotReadyError` into a wait; every other source iterator directly reads (`packages/blocks/src/runtime.ts:334-353`). A lazy pending memo first read from `$settled` therefore appears able to throw pending after the graph was considered settled, with no pending color in the component type.

```ts
const lazy = yield* $memo(load, { lazy: true });
yield* $settled(function* () {
  const value = yield* lazy;
  use(value);
});
```

I did not run this case, so I am marking it as a test request rather than a confirmed defect. If Solid guarantees that every `Source<…, true>` readable there already has a value, encode that precondition in the type; otherwise `$settled` should accept only `Read<false, E>` or gain real waiting semantics.

### Areas where D-071 is matched well

The audit should not hide what is already correct. `Errored` fallback colors now pass upward (`packages/blocks/src/flow.ts:386-435`); event binding separates failure from the may-wait marker (`packages/blocks/src/types.ts:513-550`); effect and settled failures join the component (`packages/blocks/src/runtime.ts:1203-1238`, `packages/blocks/src/runtime.ts:1254-1270`); row colors propagate (`packages/blocks/src/types.ts:581-588`); and the conformance harness keeps declared differences exact rather than normalizing them away (`packages/blocks/test/conformance/COVERAGE.md:21-40`). Those are strong examples of the meta-rule being used as an engineering rule rather than a slogan.

## 4. Risks

### Technical

- **TypeScript inference is already at its limit in visible places.** A generator `Errored` fallback needs annotated parameters because overload inference fails (`documentation/blocks-library.md:237`). Pass-through colors require explicit generics through every forwarding component, and `h(GenericComp, props)` erases them (`documentation/blocks-library.md:238`). `Props<…>`, `Source<T,E,P>`, three view flags, branded error classes, and overload-selected generator forms are coherent, but small refactors can turn a useful local error into a large “no overload matches” message.

- **The public type surface is much larger than the user model.** The root exports internal marks and runtime helpers (`READ`, `VIEW_MARK`, `COMPONENT_MARK`, `holeOf`, `runRow`, and others) plus many folding and intermediate types (`packages/blocks/src/index.ts:35-47`, `packages/blocks/src/index.ts:52-111`). That makes accidental use and compatibility promises more likely. The source calls these exports internal, but the package root exposes them.

- **Solid RC drift is intentionally allowed and therefore must be continuously earned.** The peers are `^2.0.0-rc.11` (`packages/blocks/package.json:76-79`), and the repo currently resolves rc.13 (`README.md:17`). The conformance table has only four scenarios that run server and hydration modes; the other scenarios are client-only (`packages/blocks/test/conformance/COVERAGE.md:5-19`). Large areas from the compiler experiment were not ported (`packages/blocks/test/conformance/COVERAGE.md:86-94`). A public package cannot treat one quiet two-RC move as a stable compatibility range.

- **SSR now has a useful smoke gate, but its claim is deliberately weak.** The new step uses development Vite SSR, checks that rendering ends, returns content, and emits no coded development error; it compares no markup (`examples/harness/ssr-smoke/smoke.mjs:1-23`, `documentation/blocks-gate-baseline.md:21-36`). It does not run production SSR, compare the twin with its original, or hydrate the result.

- **Hydration is the largest open technical risk.** D-082 explicitly says no gate or test hydrates a twin's server output (`documentation/DECISIONS.md:831`). The conformance hydration tests prove small patterns and show that library and compiler routes are not interchangeable (`packages/blocks/test/conformance/COVERAGE.md:42-48`), but they do not cover real router, lazy, live-source, nested-boundary, portal, or document-shell combinations. The `/profile` bug came from exactly such a composition.

- **Hydration key growth is structural, not a one-off byte cost.** The library adds two characters per nested row level versus handwritten Solid, and `/profile` reached a longest key of 22 versus 11 (`documentation/DECISIONS.md:825-831`). Deep user trees can amplify this more than the shallow aggregate percentages suggest.

- **Runtime and bundle cost are meaningful for a dialect whose main promise is semantic rigor.** The measured twins add 1–16% script time, synthetic updates add up to 27%, and the JSX flavor adds about 3.9–5.2 KB gzip (`documentation/blocks-library.md:256-291`, `documentation/blocks-library.md:335`). These are acceptable design-lab numbers, not yet a free abstraction.

- **The Vite transform has a lexical blind spot.** The exact-`function*` prefilter can skip valid source. This should block release because it makes correctness depend on formatter style (`packages/vite-plugin-blocks/src/vite.js:45-51`).

- **Foreign edges are manual trust boundaries.** The router cannot carry colors, roots that are pending can bypass the library's settled-root renderer, and foreign components are assumed colorless (`documentation/blocks-library.md:233-238`). The room route helper states its promise by hand (`examples/room-blocks/src/routes.ts:10-19`). These edges are reasonable, but a wrong annotation is unchecked runtime behavior, not just a type inconvenience.

### Product and developer experience

- **The first program needs three packages and three forms of configuration.** The user installs the runtime, Vite plugin, ESLint plugin, Solid packages, and parser, then configures plugin order, `jsxImportSource`, and type-aware lint (`documentation/getting-started.md:7-43`). That is fine for Dev as the audience, but it is a steep public entry point.

- **The call form is the main readability cliff.** Compare the original room page's direct tree (`examples/originals/room/src/routes/live.tsx:44-65`) with the twin's nested calls and generator children (`examples/room-blocks/src/routes/live.tsx:63-106`). A small child becomes `yield* Child({ … })`; a branch becomes a call with a generator; a list row becomes a generator returning `view(function* …)`. The strictness is legible once learned, but scanning UI structure becomes slower.

- **Error quality varies by layer.** Named runtime codes and branded messages such as `[SETTLED_PROP]` are good (`documentation/refusals.md:79-115`). In contrast, a generator fallback can produce a generic overload error, mistakes in a view may be reported at `view(` rather than the yield, and the handoff records that a non-`Error` attempt-handler return can print the less-specific `[ATTEMPT_ABSORBS]` text (`HANDOFF.md:130-134`). A newcomer has to know whether to read a TypeScript error, a runtime code, a transform code, or a lint rule.

- **The “one way” rule is not enforced uniformly.** Type and lint miss the unyielded component calls in todos, lint recognizes APIs by spelling, and the plugin prefilter recognizes generator spelling by raw text. Aliases and namespace imports can therefore weaken rule coverage even though runtime behavior is unchanged (`packages/eslint-plugin-blocks/src/blocks.js:19-26`, `packages/eslint-plugin-blocks/src/blocks.js:65-78`, `packages/eslint-plugin-blocks/src/blocks.js:123-130`).

- **`no-foreign-reactive` is likely to surprise mixed files.** It bans imports, not block use, so adopting blocks beside an existing plain Solid component requires splitting files even when no reactive value crosses the boundary (`packages/eslint-plugin-blocks/src/index.js:419-438`). If that is intended, the docs should say “a blocks file contains no foreign reactive imports,” not “block code uses none.”

- **Examples currently teach old and new dialects at once.** The main getting-started guide is current, but twin READMEs contain removed names, tag syntax, false cast claims, and commands that cannot run here. For a syntax-heavy library, stale examples are a functional defect.

### Process

- **The server-render blind spot was real and is now closed.** Before `f608fa7`, no gate step rendered twin pages on the server; D-082 found two failures manually. The new 16-render smoke step is the right response (`documentation/blocks-gate-baseline.md:21-37`). The remaining lesson is to add a gate when a new execution environment is introduced, not after a measurement happens to exercise it.

- **Hydration and production-server paths remain ungated.** The new smoke explicitly uses development builds and does not compare output (`examples/harness/ssr-smoke/smoke.mjs:1-5`). This is now the clearest process gap.

- **The plugin's broad no-op oracle is skipped.** The handoff says the differential test over Solid's compiler fixtures stayed behind, leaving 81 tests and one skip (`HANDOFF.md:58-63`). The frozen accepted fixtures test known transformations well, but they do not prove the plugin leaves the wider compiler corpus unchanged.

- **Performance and browser claims are detached from runnable tools in this repo.** The scripts were not carried, yet their old results remain in the main reference and twin READMEs (`documentation/DECISIONS.md:196`; `documentation/blocks-library.md:318-333`). Results should either have a runnable reproducer or be labeled historical with commit, platform, and source repository.

- **The baseline policy can hide a disappearing check.** The baseline document says a later `SKIP` on a step not present in the baseline is not a new red and must be inspected manually (`documentation/blocks-gate-baseline.md:58-74`). CI should fail when any expected step becomes skipped, especially for tool or platform failures.

- **The decision log is strong but append-only updates have left stale normative text.** D-082 contains both the old failure report and its fixes, while `blocks-library.md` stopped at the old state. A short release checklist that searches for “not fixed,” removed names, missing script paths, and old rule counts would catch much of this.

## 5. Opportunities and ideas

### What this model already enables

- The operation unions can support an exact capability report per component: reads pending, may fail with these classes, binds a handler that may wait, creates effects, or performs writes. Today those facts mostly exist to reject code. A dev-only component label could show them in an owner tree without adding runtime semantics.

- Typed failures can support boundary exhaustiveness. `Errored catch={[A, B]}` already removes handled classes from the union (`packages/blocks/src/flow.ts:398-435`). A lint or optional strict root could report the exact failures still reaching a root, instead of merely accepting that they will be rethrown.

- The may-wait marker can power a better warning than “show its in-flight state.” A type-aware lint could recognize a nearby `$optimistic`, `isPendingOf`, or explicit status source written by the same handler and suppress the warning only when there is evidence of UI feedback.

- Event transactions are a useful design primitive beyond Solid parity. Because writes before a wait are held and optimistic writes are explicit, tooling could show “committed,” “held,” and “optimistic” writes for one event (`documentation/DECISIONS.md:815-820`). That would make D-081 visible instead of surprising.

### What the compiler route should take

- Keep the host model and D-071 color algebra; erase the interpreter. The compiler can turn `yield*` into direct reads/writes, remove generator objects and proxy paths, and keep the same type-level contract.

- Recover normal component syntax without losing colors. The strict library proved why plain tags erase information; the compiler can make a tag or a lighter call carry the same child-view operation automatically.

- Infer prop colors across modules. The userland linker was correctly removed because it needed generated files and stale keys, but a compiler already owns the graph and can infer what `Props<…>` now asks the writer to repeat (`documentation/blocks-library.md:221-223`).

- Use compiler-owned hydration scopes to shorten keys and make compiler/server output self-consistent. D-069 F6 and D-082 already quantify the target (`documentation/DECISIONS.md:636-643`, `documentation/DECISIONS.md:825-831`).

- Revisit islands, server components from inert regions, and smaller runtime tiers only in the compiler route. The library's limitation list draws the right line (`documentation/blocks-library.md:225-230`).

### Simplify the library surface

- Stop exporting internal runtime marks and driver helpers from the root. `READ`, `VIEW_MARK`, `COMPONENT_MARK`, `holeOf`, `renderView`, `runRow`, and similar items should live in a private internal module or a clearly unsupported subpath (`packages/blocks/src/index.ts:35-47`).

- Review public aliases before 1.0. `SettledSource<T>` is `Source<T, never, false>`, `SettledView` is `View<false, never>`, and `TypedStore<T>` is `Path<T>` (`packages/blocks/src/types.ts:269-319`, `packages/blocks/src/types.ts:433-465`). If they are not part of user examples, remove them rather than promise several names for one idea.

- Name candidates, choosing one and not keeping aliases:

  - `isPendingOf` → `pendingOf`, to match `latestOf`.
  - `readStore` → `selectStore`, because it returns a readable selection rather than the selected value.
  - `$settled` → `$afterSettled` if the current name keeps being confused with “a settled source.”
  - Keep `attempt`, `raise`, `view`, `Loading`, and `Errored`; they are short and carry distinct ideas.

- Avoid adding a convenience alias for `Source<T,E,true>`. D-068 was right to remove `Async`: one generic source type keeps pending and failure independent (`documentation/DECISIONS.md:600-601`).

### Checks worth adding

- A type-aware `no-unyielded-component-call` rule for any call returning `ComponentView` inside block JSX, including arrays, conditionals, fragments, and foreign-component children.

- Type tests for `Loading.on`, call-form fallback colors, and `h(Loading)` fallback/on colors.

- A stream-handler type test that attempts a nested async retry and a runtime test that fixes the chosen behavior.

- Vite transform fixtures for `function *Name()`, object/class generator methods, and files that contain `yield*` but no exact `function*` substring.

- Import-aware lint recognition for aliased and namespace imports, or an explicit decision that canonical spelling is part of the dialect.

- Twin hydration tests from actual streamed HTML, plus at least one production build path.

- A docs check for missing relative links and commands, current rule/refusal counts, and removed public names.

## 6. Open design questions for Dev

### 1. What colors does `Loading.on` own?

```tsx
yield* Loading({
  on: roomKey, // Source<string, KeyError, true>
  fallback: "loading",
  children: function* () { return <Room />; }
});
```

Options:

1. Include `Ops<on>` in the output, with a test deciding whether its pending is handled locally while its failure passes upward.
2. Restrict `on` to a settled value or `Source<T, never, false>`.
3. Keep `unknown` and accept an untyped runtime read.

Recommendation: option 1. `on` is already documented and implemented as a source-capable prop; making it settled-only would be an arbitrary exception, and option 3 violates D-071.

### 2. May a stream error handler wait?

```ts
yield* attempt(
  () => stream,
  function* (error) {
    return yield* attempt(() => retry(error), toRetryError);
  }
);
```

Options:

1. Type stream handlers as synchronous block code and reject `Wait`/async event calls.
2. Change `mapStream` so the async iterator awaits a generator handler driven with the captured host semantics.
3. Disallow generator handlers for streams; accept only a plain mapping/absorbing function.

Recommendation: option 1 for the library route. Option 2 is attractive but raises hard questions about a captured event transaction after the original call has ended; option 3 throws away useful synchronous block handlers.

### 3. Is every unyielded block-component call an error inside block JSX?

```tsx
return <>{[MainSection({ filter }), Footer({ filter })]}</>;
```

Options:

1. Add a type-aware lint error unless the call is directly delegated with `yield*`.
2. Add a runtime development marker that detects a rendered block output whose bind/color receipt was never consumed.
3. Permit unyielded calls when their result is under a boundary and document them as an escape hatch.

Recommendation: option 1, plus a small set of explicit exclusions for roots/tests/foreign handoffs. Option 3 contradicts D-005 and D-062; option 2 is harder because the runtime component call returns rendered Solid content, not the type-level view object.

### 4. Can `$settled` read a source that is typed pending?

```ts
const value = yield* $memo(load, { lazy: true });
yield* $settled(function* () {
  consume(yield* value);
});
```

Options:

1. Restrict `$settled` to `Read<false, E>`, like the effect phase.
2. Make `$settled` wait for a pending read and carry that fact in its component type.
3. Keep `Read<boolean, E>` and prove with a focused runtime test that Solid always makes the value ready first.

Recommendation: start with option 3 as a test, then choose option 1 if the lazy case throws. Option 2 changes the meaning of “runs once after settle” and needs a clear second-settle rule.

### 5. Is `no-foreign-reactive` a block-use rule or a whole-file rule?

```tsx
import { createSignal } from "solid-js";

export function PlainSolidWidget() {
  const [n] = createSignal(0);
  return <span>{n()}</span>;
}

export const BlockWidget = $component(function* BlockWidget() {
  return view(function* () { return <PlainSolidWidget />; });
});
```

Options:

1. Report only a banned identifier used inside a recognized block.
2. Keep the current import ban and rename the rule/documentation to “no foreign reactive imports in a blocks file.”
3. Provide both modes, with block-use scope in `recommended` and file scope as an opt-in rule.

Recommendation: option 3. It protects the semantic boundary without forcing every gradual-adoption file split, while preserving the stronger lab discipline when wanted.

### 6. What is the minimum hydration gate before npm publication?

```ts
const html = await renderTwin("/profile");
const claimed = hydrateTwin(html, "/profile");
expect(claimed.serverNodesKept).toBe(claimed.serverNodesTotal);
expect(claimed.consoleErrors).toEqual([]);
await claimed.runOneInteraction();
```

Options:

1. Hydrate only the two rendering routes that found the recent bugs.
2. Hydrate one representative route from every SSR twin, in development and production.
3. Hydrate every route already listed in the 16-render smoke step.

Recommendation: option 2 before an experimental npm release, then option 3 before claiming general SSR support. It covers router/document/live-source differences without immediately doubling the whole gate.

## 7. Publishing readiness

### Public repository

The code is ready to be public as a design lab once the docs stop making claims the repository cannot support. The README already sets the right expectation—strict dialect, compiler route ergonomic, design lab (`README.md:3-7`)—and the decision log and conformance traces are valuable research artifacts. Before changing visibility, I would fix the stale twin READMEs, current-state sections in `blocks-library.md`, missing links, rule/refusal counts, and historical browser/performance wording. I would also add a short provenance note explaining what came from Solid, what was extracted from the fork, and what was authored here; the root license still names only Ryan Carniato (`LICENSE:1-4`) while the repository history begins at extraction (`README.md:67`).

### npm packages

These should not be published yet, even under `0.x`, for the following blocking reasons:

1. **D-071 is not clean.** Fix and test `Loading.on`, `h(Loading)` fallback/on colors, and stream generator handlers. Decide the `$settled` edge. Add the unyielded component-call lint.

2. **The Vite transform can skip valid generator syntax.** Replace the exact `function*` prefilter with the lower-level `yield` candidate check or another parser-safe check, then add fixtures (`packages/vite-plugin-blocks/src/vite.js:45-51`).

3. **Real twin hydration is untested.** The new server smoke is good but expressly does no comparison or hydration. D-082 still calls this out (`documentation/DECISIONS.md:831`).

4. **The package metadata is not release-ready.** All three packages are `0.0.0` and list Ryan Carniato as sole author (`packages/blocks/package.json:2-6`; `packages/vite-plugin-blocks/package.json:2-6`; `packages/eslint-plugin-blocks/package.json:2-6`). Keep upstream copyright attribution, but decide npm authorship and contributor/provenance fields deliberately.

5. **The optional `@solidjs/h` peer is malformed.** `peerDependenciesMeta` marks `@solidjs/h` optional, but `peerDependencies` does not declare it; it appears only in dev dependencies (`packages/blocks/package.json:76-91`). The package README promises it as an optional peer (`packages/blocks/README.md:63-65`). Add the actual peer range.

6. **The inter-package release range is unresolved.** `vite-plugin-solid-blocks` uses `solid-blocks: workspace:*` as a peer (`packages/vite-plugin-blocks/package.json:35-37`), and the handoff says the first changeset release would therefore make the plugin a major (`HANDOFF.md:60-62`). Choose the compatibility range and test the packed manifests before versioning.

7. **The tested Vite claim is unclear.** The plugin advertises `vite >=6`, develops against Vite 7, while the installed Solid Vite plugin wants Vite 8 or 9 (`packages/vite-plugin-blocks/package.json:35-55`; `HANDOFF.md:61-63`). Either test the advertised range in a matrix or narrow it.

8. **The npm documentation is stale.** The Vite plugin README has the wrong refusal count, and the package/source docs contain missing repository paths. Package READMEs are what npm users will see, so these are release blockers, not cleanup for later.

9. **Tarballs and clean consumers still need a release rehearsal.** The checked-in exports matrix is strong evidence (`documentation/blocks-gate-baseline.md:44-48`, `documentation/blocks-gate-baseline.md:117-120`), but before publishing I would run `pnpm pack --dry-run` for all three packages, inspect included README/license/type files, install the tarballs into clean JSX and `h` consumers, and run client, server, hydration, and typecheck. I did not run that rehearsal in this read-only review.

10. **State the support promise narrowly.** An honest first release should be tagged experimental, name the tested Solid RC and TypeScript version, say that compiler-route hydration output cannot mix with library-route output, and state that SSR support covers only the gated shapes. The current broad `^2.0.0-rc.11` peer range can stay only if CI becomes a real moving compatibility matrix.

My release order would be: fix D-071 and the transform prefilter; add the unyielded-call lint and twin hydration gate; clean and generate docs; settle peers, provenance, and versions; inspect tarballs in clean consumers; then publish an explicitly experimental `0.1.0`. The design is worth publishing, but its strongest promise is exactness, so the first package release should wait until the known exactness holes are closed.
